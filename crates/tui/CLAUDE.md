# crates/tui

**渲染架构（2026-07 起：永久 Fullscreen，不再有 Inline viewport）**：主循环从进程启动到退出全程运行在 `ratatui::Viewport::Fullscreen` + `EnterAlternateScreen`（`app::run_tui`），不再有 Inline/Fullscreen 切换、不再有"冻结消息写入终端真实 scrollback"这套机制。`AppState.messages` 永远保存完整会话历史，`render::build_pending_chat_lines` 每帧把全部历史当作"待渲染聊天区"交给 `render::draw_chat`；`draw()` 的布局（`Constraint::Min(3)` 撑满 chat 区剩余空间，输入框/状态栏用固定 `Length` 约束贴底）本来就是每帧从 `f.area()`（此时等于整个终端窗口）现算，因此聊天区自动撑满、输入框/状态栏自然贴着窗口最底部，不会再有"内容不够高、底部留一大片空白"的问题。历史消息的翻看改为应用内滚动：`AppState.chat_scroll`/`chat_max_scroll`/`chat_follow_tail`（`app::scroll_chat_lines`/`scroll_focus_lines`）驱动，入口以 PageUp/PageDown 等键盘操作为主。聊天消息本身不再有选中/展开状态；Thinking、ToolResult、BashOutput 标题下统一静态预览最多 3 个视觉行，超出显示 `...`，Edit/Write 自动渲染彩色 diff。Todo 与 SubAgent 仍保留独立 list/detail 交互。

**鼠标选择优先**：启动序列必须显式发送 `DisableMouseCapture`，让终端始终拥有鼠标。用户可直接拖选聊天文字，不需要 Shift/Option，松开修饰键后选区也不会被后续应用鼠标事件立即清除。这个取舍意味着应用不再依赖鼠标滚轮驱动内部历史，完整历史使用 PageUp/PageDown 等键盘入口浏览；复制最后一条 AI 回复仍可用 Ctrl+Y。不要为了恢复滚轮而无条件重新启用 `EnableMouseCapture`，否则会再次破坏原生选中。全部历史每帧都要经过 `build_pending_chat_lines`，但 `ChatMessage.md_cache`（`db9dfb6` 引入，按宽度缓存每条已定稿 assistant 消息的 markdown 渲染结果）已经把最大的开销点（markdown 重新解析）消掉，每帧只是克隆 `Vec<Line>`。

**回复中的文件/网页快捷访问**：`hyperlink::linkify_buffer` 在所有聊天内容和浮层完成后扫描最终 chat Buffer，识别 `http(s)://`、`www.`、`file://` 以及基于 `AppState.cwd` 能解析到真实文件/目录的路径（含 `path:line:column`、`#LxCy`），只给对应 cell 增加链接样式并登记屏幕坐标。不要把 OSC 8 直接塞进 `Span`/`Cell::symbol`：ANSI 字节会污染 ratatui 的宽度与 diff 计算。`HyperlinkBackend` 必须保持在 `Terminal` 完成 Buffer diff 之后才包装 OSC 8；鼠标捕获关闭时由终端原生处理 Command/Ctrl+点击，事件循环只保留防御性兜底。目标严格限制为 `http(s)://`/`file://`，系统打开命令按单个参数调用，禁止经过 shell 拼接模型文本。

**为什么这次不会重蹈 Inline 撑满高度的覆辙**：`Viewport::Fullscreen` 的构造路径是 `(area, Position::ORIGIN)`（`ratatui-0.29.0/src/terminal/terminal.rs`），完全不查询终端光标位置；而 `Viewport::Inline` 构造/resize 时（`compute_inline_size`）必须靠 crossterm 查询光标当前行才能决定往终端 scrollback 里写多少行——这个查询在 tmux/部分终端下存在渲染竞态（内部状态一致但视觉结果不稳定，严重时输入内容不可见、状态栏文字错位重叠）。这个问题已经在 Inline 方案上验证过两次都无法安全绕开：`b5729c5`（TUI 改用 Inline scrollback 那次重构）最早试过让 Inline viewport 始终撑满终端高度以消除底部空白，评估后放弃；2026-07 又按"只在空闲态才撑满"的收窄方案重试过一次，依然在用户的真实终端上复现了同一类画面撕裂，当场回退。这两次教训是"不要指望在 Inline 模式下解决贴底问题"，而不是"贴底本身做不到"——换成 `Viewport::Fullscreen` 从根上避开了那个查询，是结构性的差异，不是同一条路子换个参数再试一次。**如果以后又有人想在 Inline 模式下做贴底，先看这一段——那条路已经证明走不通。**

**Fullscreen 全程接管后，原本的 10 个"重量级管理对话框"（`/mcp` `/model` `/plugins` `/skills` `/config` `/memory` `/resume` `/agents` `/extensions` `/import`）不再需要临时切换 Terminal 变体**：它们本来就已经假设拥有整个终端来渲染，现在始终身处 Fullscreen，直接作为 `draw()` 尾部的浮层覆盖在 chat/footer 之上即可，不再有任何 `Terminal::with_options`/`clear()` 重建。权限确认框（`PermissionDialog`）因为几乎每次 Edit/Write/Bash 调用都可能弹出，归类为底部常驻面板（`BottomPanel::Permission`）而非全屏浮层，避免高频闪烁——这条不受本次改动影响。

**`open_path_in_editor`**（`/memory` 面板"用 $EDITOR 打开"）挂起 TUI 时无条件 `LeaveAlternateScreen` + `disable_raw_mode`、编辑完成后 `EnterAlternateScreen` + `enable_raw_mode` + `terminal.clear()`——这个函数写的时候就已经假设调用时处于 alternate screen（原先只在 Fullscreen 对话框打开期间才会被调用），现在全程都在 alternate screen，前置假设依然成立，不需要改。

**终端状态清理**：进程没有 `panic::set_hook`，`tui_main` 若真的 panic（而非正常返回 `Err`）会跳过 `run_tui` 末尾的 `disable_raw_mode`/`LeaveAlternateScreen` 清理，终端仍可能卡在 raw mode/alternate screen；鼠标捕获在启动阶段已经显式关闭，正常退出时再次发送 `DisableMouseCapture` 只是防御性复位。
