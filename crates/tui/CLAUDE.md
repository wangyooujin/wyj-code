# crates/tui

**渲染架构（2026-07 起：永久 Fullscreen，不再有 Inline viewport）**：主循环从进程启动到退出全程运行在 `ratatui::Viewport::Fullscreen` + `EnterAlternateScreen`（`app::run_tui`），不再有 Inline/Fullscreen 切换、不再有"冻结消息写入终端真实 scrollback"这套机制。`AppState.messages` 永远保存完整会话历史，`render::build_pending_chat_lines` 每帧把全部历史当作"待渲染聊天区"交给 `render::draw_chat`；`draw()` 的布局（`Constraint::Min(3)` 撑满 chat 区剩余空间，输入框/状态栏用固定 `Length` 约束贴底）本来就是每帧从 `f.area()`（此时等于整个终端窗口）现算，因此聊天区自动撑满、输入框/状态栏自然贴着窗口最底部，不会再有"内容不够高、底部留一大片空白"的问题。历史消息的翻看改为应用内滚动：`AppState.chat_scroll`/`chat_max_scroll`/`chat_follow_tail`（`app::scroll_chat_lines`/`scroll_focus_lines`）驱动，入口有三个——PageUp/PageDown（输入框为空时，`app.rs` 主键盘循环）、鼠标滚轮（`EnableMouseCapture` 已开启，`Event::Mouse` 分支 `MouseEventKind::ScrollUp/ScrollDown`）、Ctrl+O 展开/收起单条消息详情（`toggle_selected_message`，与滚动机制彻底独立）。

**代价（用户已知情并接受）**：`EnableMouseCapture` 开启后终端把鼠标事件整个交给应用，原生鼠标选中/拖拽复制聊天记录、终端原生 scrollback 缓冲区都不再可用（多数终端可用 Option/Shift+拖拽 等修饰键强制原生选中作为退路）。复制最后一条 AI 回复用 Ctrl+Y（已有，不受影响）。全部历史每帧都要经过 `build_pending_chat_lines`，但 `ChatMessage.md_cache`（`db9dfb6` 引入，按宽度缓存每条已定稿 assistant 消息的 markdown 渲染结果）已经把最大的开销点（markdown 重新解析）消掉，每帧只是克隆 `Vec<Line>`，超长会话下理论上仍会比"只渲染待定尾部"的旧架构略重，但不是从零到有的新问题——消息本来就一直留在 `AppState.messages` 里，冻结从来不影响内存，只影响渲染开销。

**为什么这次不会重蹈 Inline 撑满高度的覆辙**：`Viewport::Fullscreen` 的构造路径是 `(area, Position::ORIGIN)`（`ratatui-0.29.0/src/terminal/terminal.rs`），完全不查询终端光标位置；而 `Viewport::Inline` 构造/resize 时（`compute_inline_size`）必须靠 crossterm 查询光标当前行才能决定往终端 scrollback 里写多少行——这个查询在 tmux/部分终端下存在渲染竞态（内部状态一致但视觉结果不稳定，严重时输入内容不可见、状态栏文字错位重叠）。这个问题已经在 Inline 方案上验证过两次都无法安全绕开：`b5729c5`（TUI 改用 Inline scrollback 那次重构）最早试过让 Inline viewport 始终撑满终端高度以消除底部空白，评估后放弃；2026-07 又按"只在空闲态才撑满"的收窄方案重试过一次，依然在用户的真实终端上复现了同一类画面撕裂，当场回退。这两次教训是"不要指望在 Inline 模式下解决贴底问题"，而不是"贴底本身做不到"——换成 `Viewport::Fullscreen` 从根上避开了那个查询，是结构性的差异，不是同一条路子换个参数再试一次。**如果以后又有人想在 Inline 模式下做贴底，先看这一段——那条路已经证明走不通。**

**Fullscreen 全程接管后，原本的 9 个"重量级管理对话框"（`/mcp` `/model` `/plugins` `/skills` `/config` `/memory` `/resume` `/agents` `/extensions`）不再需要临时切换 Terminal 变体**：它们本来就已经假设拥有整个终端来渲染，现在始终身处 Fullscreen，直接作为 `draw()` 尾部的浮层覆盖在 chat/footer 之上即可，不再有任何 `Terminal::with_options`/`clear()` 重建。权限确认框（`PermissionDialog`）因为几乎每次 Edit/Write/Bash 调用都可能弹出，归类为底部常驻面板（`BottomPanel::Permission`）而非全屏浮层，避免高频闪烁——这条不受本次改动影响。

**`open_path_in_editor`**（`/memory` 面板"用 $EDITOR 打开"）挂起 TUI 时无条件 `LeaveAlternateScreen` + `disable_raw_mode`、编辑完成后 `EnterAlternateScreen` + `enable_raw_mode` + `terminal.clear()`——这个函数写的时候就已经假设调用时处于 alternate screen（原先只在 Fullscreen 对话框打开期间才会被调用），现在全程都在 alternate screen，前置假设依然成立，不需要改。

**终端状态清理**：进程没有 `panic::set_hook`，`tui_main` 若真的 panic（而非正常返回 `Err`）会跳过 `run_tui` 末尾的清理代码（`disable_raw_mode`/`LeaveAlternateScreen`/`DisableMouseCapture`），终端可能卡在 raw mode/alternate screen/鼠标捕获状态——这是已存在的风险（此前 9 个 Fullscreen 对话框运行期间 panic 同样会中招），现在只是多了鼠标捕获这一项状态需要还原，不是新引入的风险类别。
