# crates/tui

**渲染架构（2026-07 起：永久 Fullscreen，不再有 Inline viewport）**：主循环从进程启动到退出全程运行在 `ratatui::Viewport::Fullscreen` + `EnterAlternateScreen`（`app::run_tui`），不再有 Inline/Fullscreen 切换、不再有"冻结消息写入终端真实 scrollback"这套机制。`AppState.messages` 永远保存完整会话历史，`render::build_pending_chat_lines` 每帧把全部历史当作"待渲染聊天区"交给 `render::draw_chat`；`draw()` 的布局（`Constraint::Min(3)` 撑满 chat 区剩余空间，输入框/状态栏用固定 `Length` 约束贴底）本来就是每帧从 `f.area()`（此时等于整个终端窗口）现算，因此聊天区自动撑满、输入框/状态栏自然贴着窗口最底部，不会再有"内容不够高、底部留一大片空白"的问题。历史消息的翻看改为应用内滚动：`AppState.chat_scroll`/`chat_max_scroll`/`chat_follow_tail`（`app::scroll_chat_lines`/`scroll_focus_lines`）驱动，PageUp/PageDown 与经过终端输入分流的鼠标滚轮共用这一路径。聊天消息本身不再有选中/展开状态；**ToolResult 与 Thinking 默认折叠成一行标题**（工具结果只留 `⏺ Bash(...) · 0.0s`，thinking 留 `⎿ 已思考 12s（41 行）  ·  Ctrl+O 展开`），`Ctrl+O` 全局切换后出**全文**、不再有任何行数上限——**不要给任何一类可折叠正文改回 per-message 选中展开**，`crates/tui/src/app.rs` 里那条 `_ => leave_content_focus()` 兜底和 Enter「回输入框」的语义都是按"聊天区无选中"设计的。**两个例外**：① `!` bash 输出（`MessageRole::BashOutput`）保持标题行 + 三行预览 + `...`，即 `TASK_PREVIEW_MAX_ROWS` / `push_capped_preview_lines` 现在只服务这一条路径；② **Edit/Write 的彩色 diff 折叠态仍然内联可见**（`render_collapsed_diff_preview`，上限 `COLLAPSED_DIFF_MAX_LINES = 20` 行，超出折成一行 `… 还有 N 行（Ctrl+O 展开全文）`）。②的理由是**diff 才是这次调用的结果**，回执「已替换 1 处」信息量为零——折叠掉它等于用户必须先按 Ctrl+O 才知道这次编辑改了什么，对一个以改代码为主业的 CLI 不可接受（对齐 Claude Code）。它**不破坏**下面那条「折叠态一律不得触碰 content」的不变式：Edit/Write 的回执在工具层就被 `MAX_DIFF_LINES = 200` 封顶、构造开销有硬上界，且渲染只取前 20 行；`Bash` 那种动辄几 MB 的输出仍然一个字符都不碰。**不要把这个例外扩大**——把它推广到所有工具就等于把每帧 `lines().collect()` 的浪费请回来。Todo 与 SubAgent 仍保留独立 list/detail 交互，其中 Todo 详情面板的 `ChatRenderCtx` 跟随同一个 `output_expanded` flag（它重放的是**工具消息**，硬编码 false 会让面板只剩一排标题、正文全空）。

**shells / subagents 面板只列运行中的条目（v1.5.21+）**：两个面板的口径统一为「只显示 `Running`」，完成即从列表消失——对齐 Claude Code。**唯一口径分别是 `AppState::running_shells()` 与 `AppState::visible_sub_agents()`**，`draw_shell_panel` / `draw_sub_agents_panel` / `bottom_panel_size` / `shell_panel_height` / `move_selected_*` / `focus_*_edge` / `/shells` 与 `/subagents` 的定位逻辑**全部**必须走它们，不要有第二处直接遍历 `state.shells` / `state.sub_agents` 做展示决策——**两套口径漂移一次就会复现「列表里有个按不动的幽灵行」**。底层 `state.shells`（Vec，只增不减）与 `state.sub_agents`（BTreeMap）**保留全部条目**：退出状态要留在里面等 `poll_shells` 读、自动唤醒 reminder 也要读，面板只是不再展示它们。移除条目的动作挂在状态翻转处（`poll_shells` 检出退出、`E::Done`、interrupt 控制、ESC 中断），每次翻转后调 `reconcile_shell_selection` / `reconcile_sub_agent_selection`：选中项若已不在列表里就落到最后一个运行项，一个都不剩时收起面板并把 `ui_focus` 交还 `Composer`（否则焦点悬空在看不见的一行上，用户按 ↑↓ 才发现出事了）。**已完成的条目并非不可查**：子 Agent 完整轨迹仍落盘，可用 `wyj-code subagent-trace <session> [id]` 读；shell 输出早已通过 `bg_shell_done_reminder` 回灌模型、聊天流也留了 `bash_N 已退出` 记录。

**Thinking 三条不可回退的理由**（`render.rs::render_thinking_block`）：① 折叠头用 `⎿`(U+23BF) 而非旧实现的 `✻`(U+273B)，后者属 Dingbats 区，终端字体覆盖率低一个量级，缺字形时画成豆腐块；② 行数统计的是**去空行后的原始行数**，与屏幕上的**视觉行数**（折行后再截断）没有对应关系，所以它只能当元信息、不能当"下面还有多少内容"的提示；③ 流式期间（`live: true`）**完全不碰 `content`**——旧实现每帧把整个 `thinking_buf` 重新折行一遍、再只取前 3 行扔掉，长 thinking 下是纯浪费。耗时来自 `AppState.thinking_started`（`flush_thinking` 在清空前算出并落到 `ChatMessage::thinking_elapsed_secs`；该字段自 ThinkingDelta 首块写入后曾长期只有写点零读点），`/resume` 的旧会话没有耗时，故有 `thinking.done_no_elapsed` 分支而不是显示假的 `0.0s`。

**③ 已泛化成全局不变式：折叠态一律不得触碰 `content`。** 工具结果折叠（v1.5.19）把这个教训外推到了 ToolResult——`render_tool_result_block` 在调 `render_tool_result_preview`（它会把整个 `content` `lines().collect()` 成 Vec）**之前**就 return。旧实现每帧为每条工具结果构建完整 preview 再只取 3 行扔掉，与 thinking 流式态是同一类纯浪费。测试 `collapsed_tool_result_never_touches_content` 是这条不变式的回归钉子：任何人把 `return` 挪晚、或提前构造 `content_lines`，它立刻变红。**唯一的显式豁免是 Edit/Write 的 diff**（见上段的例外②）——该钉子用的样本是 `Bash` + 100KB 正文，因此仍然有效；判断豁免是否越界的标准是**正文有没有工具层的行数上界**（Edit/Write 有 `MAX_DIFF_LINES = 200`，Bash 没有）。给一个无上界的工具开同样的例外 = 这条不变式作废。

**哪些内容加工逻辑留、哪些随折叠删了**（工具结果展开态）：判据是「这段逻辑的动机里有没有『名额 / 预算 / 挤到视野外 / 浪费在…』」。**随折叠删掉的纯预算启发式**：`push_capped_preview_lines` 的 `take(3)` + `...`、错误输出的 head+tail `⋮`（它当初存在是为了保住尾部的 `request_id`/`reason`，展开后尾部天然可见，保留反而会主动删掉用户明确要求看的中间内容）、非 diff 的空行过滤（空行在全文里是段落分隔，删掉会压平 AskQuestion 这类结构）。**与预算无关、必须保留的表达层规范化**：`is_exit_code_banner`（`bash.rs` 拼这行是**给模型看的**，对人类是纯冗余）、`strip_read_line_number`（传输层的 `N\t` 前缀，纯噪音还加剧折行）、Edit/Write 的 diff 起点定位（diff **才是**结果，回执不是，且找不到 diff 特征行时 `.unwrap_or(raw)` 回落全量）、is_error 首行红/其余 dim（视觉噪音控制；展开态下论证更强——400 行错误块刷成一片红比 3 行时糟糕得多）。渲染空行必须 push 成真正的 `Line::from("")` 而非带缩进 span 的空白行，否则 `trim_trailing_blank_lines`（只弹 `spans.is_empty()`）弹不掉，每个工具结果尾部会留一行拖尾空格。

**鼠标选择优先**：启动序列必须显式发送 `DisableMouseCapture`，让终端始终拥有鼠标。用户可直接拖选聊天文字，不需要 Shift/Option，松开修饰键后选区也不会被后续应用鼠标事件立即清除。Ghostty 在 alternate screen + 无鼠标报告时会用 DEC mode 1007 把滚轮转为 `ESC[A`/`ESC[B`，与普通方向键在 crossterm 事件层的结果相同；`TerminalWheelRouting::GhosttyKeyReleases` 通过 Kitty `REPORT_EVENT_TYPES` 的 release/repeat 事件区分真实键盘与滚轮伪键，滚轮只调用 `scroll_focus_lines`，不得进入 `navigate_input_or_history`。非 Ghostty 或 tmux/zellij 路径下不能假定 release 可靠透传，必须用 XTSAVE/XTRESTORE 成对保存、关闭、恢复 mode 1007，至少保证滚轮不会污染输入历史。不要为了恢复滚轮而无条件重新启用 `EnableMouseCapture`，否则会再次破坏原生选中。复制最后一条 AI 回复仍可用 Ctrl+Y。全部历史每帧都要经过 `build_pending_chat_lines`，但 `ChatMessage.md_cache`（`db9dfb6` 引入，按宽度缓存每条已定稿 assistant 消息的 markdown 渲染结果）已经把最大的开销点（markdown 重新解析）消掉，每帧只是克隆 `Vec<Line>`。

**UI 线程绝不能 `await` session 锁**（`try_session_lock`）：回合 task（`spawn_agent_turn` + 两处内联 turn task）在**整个 agent 回合期间**持有 `session` 这把 `tokio::sync::Mutex`——LLM 往返加全部工具调用都在锁内，一次长回合动辄几分钟。主循环任何一处 `session.lock().await` 都会让整个界面停在那一帧：**不重绘、不读按键**（`event::poll` 在这些点之后），连排在保存分支上游的 `abort_stalled_turn()` 看门狗都跑不到下一轮，ESC/Ctrl+C 全部失效——用户看到的就是「执行久了卡死不动」。**这条规则的两端**：① 主循环里凡是碰 session 一律走 `try_session_lock`，拿不到就 `notify_session_busy()` + 跳过本帧（保存路径保留 `save_needed = true` 下一帧重试；命令路径 `anyhow::bail!` 走它自己的错误通道；会话选择器保留不关）。**回合 task 内部的 `lock().await` 不要动**——那正是持锁者。后台 task（如 `spawn_plan_approval_checkpoint`）可以等锁，它不在 UI 线程上。② 终态事件（`Usage` / `TurnDone` / `Error`）走**阻塞式** send（`mpsc::channel(256)`），必须**先 `drop(sess)` 再发**：UI 收到 TurnDone 后置 `save_needed`、下一帧就来取锁，turn task 若还持锁就是环形等待。③ **主循环无条件区段里拿不到锁时只能「跳过这件事」，不能 `continue`**：`continue` 跳回的是整个循环，会连带跳过紧随其后的 `ui_ask_rx` 消费与 `event::poll()`——按键、权限确认弹窗、AskQuestion、计划批准全停摆，而 `terminal.draw()` 在它之前、画面照常刷新，用户看到的是「界面活着但按键全哑」，ESC/Ctrl+C 也救不回来（真正终止回合的是排在 `continue` **上游**的心跳看门狗，现场更像「莫名卡几分钟后自己恢复」）。`TurnDone` 置位 `save_needed` 与自动唤醒/排队兜底的 spawn 发生在同一帧，所以每条排队消息触发的自动续跑都会踩中，整回合失灵。`event::poll()` 按键块**内部**的 `continue` 没问题（消费一个按键、下一帧继续）。钉子：`every_turn_task_releases_the_session_lock_before_terminal_events`（静态检查三处 turn task 的「锁内取 Usage 快照 → drop → 发」顺序）、`try_session_lock_never_waits_for_a_running_turn`（带超时兜底，改回 await 就会挂在 timeout 上）、`autosave_never_continues_past_the_input_layer`（静态检查 autosave 分支内不得出现 `continue`）。

**`pending_queue` 是 steer 队列的镜像，必须跟着真实水位走**（`reconcile_pending_queue`）：入队时 `pending_queue` 与 `core::SteerQueue` 各加一条，正常靠 `AgentEvent::Injected` 出队。共享队列之后**取走者不再唯一**——主 Agent 排空全部、前台子 Agent 只排空 `UserMessage`（`SystemReminder` 是给主 Agent 的后台结论，被抢走就双双丢失）、嵌套子 Agent 同享同一份；子 Agent 没有 UI 事件通道、`on_inject` 是空闭包，**发不出 `Injected`**。镜像于是停在旧水位，回合结束后兜底重发会把已经投递给子 Agent 的消息**再当一条全新用户消息发一遍**，直接违反「一条内容只投递一次」。因此 `TurnDone` / `Error` 里必须在 `injector` 被清空**之前**调用 `reconcile_pending_queue()`，按 `queue.pending_user_messages()` 把镜像裁到真实水位——按水位而不是「谁取走的」，三种取走路径一律正确。钉子：`subagent_drained_steerage_is_not_resent_as_a_new_user_message`（已投递的不得重发）、`undelivered_steerage_survives_reconciliation_for_the_race_fallback`（没投递的必须留下，否则真正的竞态兜底会吞掉用户输入）。

**文本编辑按键只有一份实现**（`input::apply_edit_key`）：主输入框、`InputOwner` 借用态（/model /mcp /skills /plugins /schedule 的配置输入）、AskQuestion 与计划批准的"其他"自由输入**全部走它**。历史上有三套各写各的按键表，弹窗那套只有打字/退格/左右，同一个编辑动作换个界面就按不动——这是"交互反人类"的根因。`InputBox` 的原语（`move_word_*` / `kill_*_of_line` / `delete_word_backward` / `delete_char_forward`）一直齐全，缺的只是接线，所以**新增编辑键一律加在这里，不要在调用方单独实现**。刻意**不含** `Enter` / `Esc` / `Tab` / `↑` `↓` / 粘贴：各有应用层语义（提交、取消、翻页、历史、附件），由调用方分发；唯一例外是 `Shift+Enter`（所有输入场景都只表示换行）。主输入框有 5 个键不走共享实现，原因写在代码注释里：`Backspace` / `Delete` / `Ctrl+W` 要连带删附件占位标记，`Home` / `End` 在输入框为空时是"跳到对话首尾"。换行有三种等价写法：`Shift+Enter`（终端支持键盘协议时）/ `Ctrl+J` / 行尾 `\` + `Enter`，后两种是兜底——`Shift+Enter` 在 tmux 默认设置下会被原样报成普通 Enter 直接提交。自由文本的光标用**反色块**而不是移动硬件光标（弹窗是浮层，硬件光标被底部输入框占用，两者会打架）；嵌套弹窗必须贴着父面板摆放，不要和父面板用同一个整屏 `area` 居中（会叠在父面板上，看着像渲染错位）。

**多行输入必须逐行画出来，面板高度跟着行数走**：AskQuestion 的「其他」和计划批准的「手动输入」都接了 `apply_edit_key`，因此都是多行的，提交时取的是 `input.text()`——**只画第一行 = 所见非所发**（用户写三行只看见一行，回车却把三行一起发出去）。两个面板统一走 `render::freetext_line`（真实块状光标 + 超宽横向滚动），`bottom_panel_size` 对 PlanApproval 的高度按 `3 + input.lines.len()` 算，不要写死。横向滚动的 `visible_window` 不变式是**光标之前的文本必须完整落在窗口内**，否则光标被挤出可视区、整块反色消失（比旧的假 `_` 更糟：旧的永远错但永远看得见）；向后走时减的是「即将丢到左窗外的字符」、比的是「留在窗口内的前缀宽度」，反过来写会让光标偏移量无界增长，行宽超过约 `2 × inner_w` 后必然消失，且 CJK 光的预留必须按 `char_width`（2 列）而不是写死 1。钉子：`cursor_stays_visible_on_long_lines`、`window_never_exceeds_available_width`、`freetext_lines_are_all_rendered`、`freetext_can_hold_multiple_lines`。

**附件占位符必须两处同源**（`render::attachment_display_text`）：输入框里的 `[Image #1]` / `[File: name]` 与聊天区里那条用户消息的展示文本**必须逐字节相同**，且占位符停在用户粘贴它的那个位置。附件位置信息只存在于 `InputBox` 的内部原子标记 `ATTACHMENT_MARKER` 里，`InputBox::text()` 会把它们过滤掉，所以**展示文本必须在 `input.take()` 之前算好**（发送路径先 `input.clone()` 留快照）——事后从 `text + attachments` 现拼只能得到「正文末尾追加一行附件列表」，那正是这个 bug 的形态：同一个附件在输入框是 `[Image #1]`、在消息区变成 `[图片 402×288]`，用户会以为发送丢了图或换了一张。因此凡是消息要离开输入框的路径（`pending_queue: Vec<OutgoingMessage>`、`ExecModeConfirmDialog::pending_display`）都必须把 `display` 一起带走，**不允许在消费端重算**。无标记的附件（正文里 `@path` 展开出来的文件）由 `attachment_display_text` 在末尾单列，注意只投影 `attachments[..marked]`——`input_with_attachment_placeholders` 末尾那段「旧状态兼容」兜底会把无标记附件补进行首，两者同时生效就是同一个附件出现两次。`reconstruct_display`（`/resume`）另有一处：图片块此前被 `_ => {}` 整个吞掉，恢复历史会话后聊天流里不留任何痕迹，现补 `[Image #n]`（位置信息从未落盘，只能在末尾）。回归钉子：`chat_display_is_byte_identical_to_the_input_box`、`at_referenced_files_without_a_marker_are_listed_at_the_end`、`user_images_survive_into_the_reconstructed_display`。

**回复中的文件/网页快捷访问**：`hyperlink::linkify_buffer` 在所有聊天内容和浮层完成后扫描最终 chat Buffer，识别 `http(s)://`、`www.`、`file://` 以及基于 `AppState.cwd` 能解析到真实文件/目录的路径（含 `path:line:column`、`#LxCy`），只给对应 cell 增加链接样式并登记屏幕坐标。不要把 OSC 8 直接塞进 `Span`/`Cell::symbol`：ANSI 字节会污染 ratatui 的宽度与 diff 计算。`HyperlinkBackend` 必须保持在 `Terminal` 完成 Buffer diff 之后才包装 OSC 8；鼠标捕获关闭时由终端原生处理 Command/Ctrl+点击，事件循环只保留防御性兜底。目标严格限制为 `http(s)://`/`file://`，系统打开命令按单个参数调用，禁止经过 shell 拼接模型文本。

**为什么这次不会重蹈 Inline 撑满高度的覆辙**：`Viewport::Fullscreen` 的构造路径是 `(area, Position::ORIGIN)`（`ratatui-0.29.0/src/terminal/terminal.rs`），完全不查询终端光标位置；而 `Viewport::Inline` 构造/resize 时（`compute_inline_size`）必须靠 crossterm 查询光标当前行才能决定往终端 scrollback 里写多少行——这个查询在 tmux/部分终端下存在渲染竞态（内部状态一致但视觉结果不稳定，严重时输入内容不可见、状态栏文字错位重叠）。这个问题已经在 Inline 方案上验证过两次都无法安全绕开：`b5729c5`（TUI 改用 Inline scrollback 那次重构）最早试过让 Inline viewport 始终撑满终端高度以消除底部空白，评估后放弃；2026-07 又按"只在空闲态才撑满"的收窄方案重试过一次，依然在用户的真实终端上复现了同一类画面撕裂，当场回退。这两次教训是"不要指望在 Inline 模式下解决贴底问题"，而不是"贴底本身做不到"——换成 `Viewport::Fullscreen` 从根上避开了那个查询，是结构性的差异，不是同一条路子换个参数再试一次。**如果以后又有人想在 Inline 模式下做贴底，先看这一段——那条路已经证明走不通。**

**Fullscreen 全程接管后，原本的 11 个"重量级管理对话框"（`/mcp` `/model` `/plugins` `/skills` `/config` `/memory` `/evolve` `/resume` `/agents` `/extensions` `/import`）不再需要临时切换 Terminal 变体**：它们本来就已经假设拥有整个终端来渲染，现在始终身处 Fullscreen，直接作为 `draw()` 尾部的浮层覆盖在 chat/footer 之上即可，不再有任何 `Terminal::with_options`/`clear()` 重建。权限确认框（`PermissionDialog`）因为几乎每次 Edit/Write/Bash 调用都可能弹出，归类为底部常驻面板（`BottomPanel::Permission`）而非全屏浮层，避免高频闪烁——这条不受本次改动影响。

**ProfileDialog 还兼任首次启动缺 API Key 的 onboarding 入口**：`wyj-code` 在 `~/.wyj-code` 缺失时通过 `ProfileDialog::new_for_onboarding` 自动打开（焦点预置到 `PROFILE_API_KEY_FIELD_IDX = 5`），用户填写后 `profile_try_save` 经 `rebuild_fn` 重建 agent，无需重启。详见 `crates/cli/CLAUDE.md` "首次启动缺 API Key 的处理"。

**`/evolve` 治理中心**：`EvolutionDialog` 固定提供 Active / Candidates / Episodes / Health 四视图，Tab/Shift+Tab 循环，列表与右侧 evidence/detail 保持独立滚动，PageUp/PageDown 只移动详情。Approve、Reject、Forget、Rollback 都必须先进入 `EvolutionConfirmAction` 二次确认；切换视图、Esc 或完成动作后清空确认状态，避免旧确认落到新选中项。Episode 的 good/bad feedback、external include 与 manual skillize 可以直接执行，但必须在面板中展示成功或错误结果；Skill 批准前先创建 checkpoint，默认只安装到 project scope，任何 Skill/lockfile/candidate 状态写入失败都调用生成 Skill 回滚。对话框 reload 只能刷新下一次视图快照，不能改变正在执行的 Agent 回合 Evolution context。

**`open_path_in_editor`**（`/memory` 面板"用 $EDITOR 打开"）挂起 TUI 时无条件 `LeaveAlternateScreen` + `disable_raw_mode`、编辑完成后 `EnterAlternateScreen` + `enable_raw_mode` + `terminal.clear()`——这个函数写的时候就已经假设调用时处于 alternate screen（原先只在 Fullscreen 对话框打开期间才会被调用），现在全程都在 alternate screen，前置假设依然成立，不需要改。

**终端状态清理**：v1.5.12 引入 `crates/tui/src/panic_guard.rs`，`cli::main()` 入口最前 `wyj_tui::panic_guard::install()` 注册进程级 `panic::set_hook`（`take_hook` 链式保留前一个 hook），`run_tui` 内 `enter_terminal_screen` 成功后 `mark_active()`、`leave_terminal_screen` 成功后 `mark_inactive()`（全局 `AtomicBool TUI_SCREEN_ACTIVE`），panic 触发时 hook 检查到 active 就 best-effort 还原终端（`DisableMouseCapture` → `LeaveAlternateScreen` → `disable_raw_mode` → `Show`，每步吞错）再调 prev hook 写 panic 信息。背景是 2026-09 用户跑 `stock_fenxi` 项目时 `memory_v3.rs:977` 的 `String::truncate(MAX_CONTEXT_BYTES)` 撞到 CJK char boundary panic，panic 输出叠加在 alternate screen 上造成排版撕裂（已被 `wyj-core::textutil::floor_char_boundary` 治本）。后台 tokio worker 线程 panic 也会触发（worker 无 TTY，crossterm 命令失败但错误吞掉，可接受）。鼠标捕获在启动阶段已经显式关闭，正常退出时再次发送 `DisableMouseCapture` 只是防御性复位。

## 终端 panic 还原与字符边界安全

18. **TUI 终端 panic 还原 + char-boundary 安全工具（v1.5.12）**：
    - **`crates/tui/src/panic_guard.rs`** 新增进程级 `panic::set_hook`：在 `cli::main()` 入口最前 `wyj_tui::panic_guard::install()` 注册（`take_hook` 链式保留前一个 hook），`run_tui` 内 `enter_terminal_screen` 成功后 `mark_active()`、`leave_terminal_screen` 成功后 `mark_inactive()`（全局 `AtomicBool TUI_SCREEN_ACTIVE`），panic 触发时 hook 检查到 active 就 best-effort 还原终端（`DisableMouseCapture` → `LeaveAlternateScreen` → `disable_raw_mode` → `Show`，每步吞错）再调 prev hook 写 panic 信息。背景：TUI 进入 alternate screen + raw mode 后若进程 panic，会跳过 `run_tui` 末尾清理，导致终端卡死 + 下次启动画面残留 frame + panic 写 stderr 覆盖 ratatui cell 造成画面撕裂。代价是后台 tokio worker 线程 panic 也会触发（worker 无 TTY，crossterm 命令会失败但错误吞掉，可接受）。
    - **`crates/core/src/textutil.rs` 新增 `floor_char_boundary(&str, usize) -> usize`**：按字节切字符串时（如 `String::truncate(MAX)`），先把上限回退到最近的 char boundary 再 truncate，避免 `String::truncate` 在 CJK / emoji 多字节字符中间触发 `is_char_boundary` assertion panic。`memory_v3.rs` 拼装 Active Memory 上下文超过 `MAX_CONTEXT_BYTES` 时接入；与 `wyj-tools::textutil::truncate_str`（返回 `&str`）分工——这里是 `usize` 索引版本，配合 `String::truncate` 做原地截断避免重复分配。
    - **TUI 标题栏 / 状态栏文案简化（v1.5.12）**：`thinking_status_label` 改回单层优先级静态字符串（InProgress TodoItem 的 `active_form` 或 `content` → current_op 映射 `Reading file / Running command / Editing file / Updating todos / Delegating task / Browsing / Preparing plan / Running <Tool>` → permission_dialog → plan_dialog → pending_queue → fallback `Thinking`），砍掉旧的"大象装进冰箱"4 秒旋转短语——非功能性、多语言干扰、跨平台兼容性差。`draw_input` 标题栏只在 thinking 态保留 `⠋ {label}{suffix}`（spinner + label + animated dots）+ 加粗品牌橙；非 thinking 态 Plan/Bypass/Normal 三种模式标题栏分别精简为 `[plan] Enter to send` / `[bypass] Enter to send` / `Enter to send`，把 `↑↓ history / Shift+Enter newline / ! bash / / commands / Shift+Tab mode` 等长串提示砍掉（这些在顶部 `/help` 与 docs 里有完整说明）。状态栏（`draw_status`）默认右侧不再放 `ctrl+d or ctrl+c twice to exit  /help`，留给左侧"模型 / 进度 / 用量 / cwd"；thinking 指示器单点（标题栏）而非上下两处同闪烁。删除旧 `draw_input` 在 `is_thinking=true` 时提前 `return` 的逻辑——那个 `return` 跳过了末尾 `f.set_cursor_position`，crossterm 硬件光标永远停在"上次成功提交"位置、用户感觉光标卡死；现实现里 thinking 态仍调 `set_cursor_position` 让光标跟随用户实际操作，配套新增两个 `TestBackend` 回归测试（`draw_input_keeps_cursor_visible_while_thinking` + `draw_input_title_shows_thinking_spinner_when_thinking`）防止再次回归。
    - **底部两行改为「实时进度 / 常驻身份」（v1.5.20）**：把 v1.5.12 那条里的 `{label}{suffix}`（animated dots）与状态栏的 `total ↑↓ 用量`、`已自动压缩 ×N` 全部换掉。**输入框标题栏**（`draw_input` thinking 态）现在是 `⠋ <当前这一步> · <这一步耗时> · <本轮 token ↑↓`：label 优先取 `current_op` 原文（`Bash(cargo test)`）而非旧的固定短语映射（`Running command`），耗时由新增的 `AppState.current_op_started` 给出、语义是"这一步跑了多久"、无工具在跑时回落整轮耗时，token 取 `turn_live_input/output_tokens`。**animated dots 已删除**（与耗时/用量同时动会发飘，窄屏最先被挤掉），spinner 帧是唯一的运动效果。**token 的实时数据源只能是 `AgentEvent::UsageDelta`（`with_usage_callback` 逐请求回调）**——`AgentEvent::Usage` 只在**整回合收尾**时推一次 session 累计（`total_*` 在回合进行中纹丝不动），拿 `total_* - turn_start_*` 做差会让标题栏整个回合都显示 `0↑ 0↓`；所有发起回合的入口（用户消息/排队注入/自动唤醒/slash 命令展开的 prompt）统一走 `AppState::begin_turn_timing()` 归零实时计数器，漏一处就会把上一轮的量带进下一轮。**状态栏**（`draw_status`）收成三段常驻：`◆ <模型> [plan|bypass|default] · <cwd>`，三种模式**全部显式标注**（旧实现 Normal 不显示任何标记，"看不到标记"无法区分是 Normal 还是芯片被挤出屏幕）；**Bypass 三处同色为红**（状态栏芯片 + 标题栏 `[bypass] Enter to send` + 输入框边框），它等价于"本次会话跳过全部权限确认"，黄色偏中性、承担不了提醒职责；`已自动压缩 ×N` 下线（压缩情况改查 `/context`）。右侧仅在排队 / Ctrl+C 待确认时出现临时提示，平时为空。回归钉子：`draw_input_title_shows_step_elapsed_and_turn_tokens_when_thinking`（四段整帧断言）、`title_token_text_ignores_session_usage_that_only_lands_at_turn_end`、`draw_status_labels_every_mode_and_paints_bypass_red`、`usage_delta_accumulates_this_turn_and_resets_on_next_turn`。

## 后台任务可见性与自动续跑

20. **后台任务可见性与自动续跑（v1.5.16+）**：解决"派完活就不动"和"后台输出看不见"两个问题。
    - **自动唤醒**（`app.rs` 主循环 idle 钩子）：后台 subagent 结果此前只进 `pending_bg_reminders` 等用户下一条消息、后台 shell 更只返回 `bash_N` id 靠模型自己轮询 `BashOutput`，两条路都停在等用户输入。现在 idle 时 `AppState::poll_shells()` 同步 `BashSessionManager::global().list()` 到 `shells`，检测到退出就把 `prompts::bg_shell_done_reminder`（含输出尾部，经 `truncate_head_tail` 收口到 4KB）推进 `pending_bg_reminders`；**第二个独立 if 块**在 `!is_thinking && !pending_bg_reminders.is_empty() && !auto_wake_paused` 时起新 turn。多任务同帧完成**合并成一轮**（`reminders.join("\n\n")`），避免连续多次 LLM 往返。
    - **两种回合必须区分**：`spawn_agent_turn` 的 `text: Option<String>`——`Some(用户输入)` 常规回合，`None` 自动唤醒回合（reminder 本身就是这一轮唯一 user 输入）。若自动唤醒时传 `Some(reminder 原文)`，reminder 会被当成"用户说的话"写进 session 历史并在 `/resume` 后继续显示。聊天流侧只 push `ChatMessage::system(tr("bg_wake.notice"))`，不暴露 reminder 原文。
    - **ESC 保护**：`AppState.auto_wake_paused` 在 `interrupt()` 置 true、`begin_new_turn()` 清 false——用户主动打断意味着"先别继续"，此时后台任务完成也不该自动唤醒（会显得不听话）。
    - **只读快照 API**（`bash_session.rs::BackgroundJob::tail(max_bytes)`）：面板每帧要读输出，但 `read_new()` 推进的是 `BashOutput` 工具的增量读游标，两者共用会互相抢内容（面板看到空白、工具看到"无新输出"）。`tail` 按 char boundary 收口（中文/emoji 安全）且**不推进游标**。**新写 UI 侧读输出时不要用 `read_new()`。**
    - **退出误唤醒**：`kill_all()`（`app.rs` 退出路径 + `cli/main.rs` headless）给所有 Running job 发 SIGKILL，但 `spawn_prepared` 里的 `child.wait()` task 仍会把它们翻成 `Exited(-1)`。轮询检测**必须**用 `!state.should_quit` 守卫拦在前面，否则退出那一帧会把每个后台任务都误判为"刚完成"并触发唤醒。
    - **两级生命周期粒度**：`begin_new_turn()`（每轮对话）**刻意不清** `shells`——dev server 等任务跨轮次持续存在，在这儿清会让它们从面板凭空消失；真正作废的是 `reset_for_new_session()`（`/clear`/新会话/resume），那里进程本身也已被 `kill_all` 收走。
    - **面板优先级**（`render.rs::bottom_panel_size`）：`Shells` 与 `SubAgents` 互斥（底部只有一个位置），规则是**用户焦点优先，其次按"有运行中任务"**。两者常同时跑（派 agent 改代码 + 自己起 dev server），固定先后会让其中一方永远看不见也按不了 k。跨区链条 `Chat ↓ → Todos ↓ → SubAgents ↓ → Shells`，`UiFocus` 需在 6 处 match 里同步加分支（`move_focus_selection` / `scroll_focus_lines` / `content_focus_active` / `enter_content_focus` / `leave_content_focus` / `toggle_focused_content_detail` / `close_panel_focus`）。
    - **详情区 scroll 语义**：`draw_shell_panel` 与 `draw_sub_agents_panel` 一致——`clamped` 是"从底部往上偏移的行数"，`clamped=0` 即贴底跟随新输出，用户 PageUp 后停在历史位置。渲染时用 `Paragraph::line_count` 重算并 clamp 写回 `shell_detail_max_scroll`（`draw()` 每帧先防御性清零）。
    - **`k` 键无冲突**：裸 `k` 在内容区焦点态未占用；输入框的 `Ctrl+K`（kill-to-end）走 `key.modifiers.contains(CONTROL)` 另一条分支。`kill_selected_shell` 必须 `&mut self`（要 push 提示消息），且 `BashSessionManager::kill` 是 async（等 2s 兜底 SIGKILL），经 `state.kill_tx` 把 `AgentEvent::ShellKilled` 发回 UI 线程。
    - **tasklist 摘要**：`push_inline_todo_lines` 在 `all_done` 时只画一行摘要（保留耗时/token 统计的可追溯信息），不画分隔线/条目/展开提示。`TurnDone` **刻意不清** `current_todos`（测试 `turn_done_auto_completes_remaining_in_progress_todos` 用 `expect` 锁死了该行为），所以"全部完成 → 下一条消息之间"面板会一直存在，收成一行是唯一能在不改该测试的前提下消掉干扰的办法。`Ctrl+T` 在 `all_done` 时 no-op（否则展开一个永远渲染不出来的空壳）。
