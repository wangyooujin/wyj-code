# v1.4 computer-use 人机互不干扰调研与实施方案

> 状态：核心方案已实施，2026-07-21  
> 目标：computer-use 与人类用户可以并行使用同一台机器；默认路径不抢鼠标、不抢键盘、不切前台焦点，用户无需处理“是否继续”弹窗。

### 实施记录

本版本已落地解决同一 macOS GUI 会话冲突所需的核心闭环：`WindowTarget` 稳定身份与按窗口截图、`app_computer` AX/目标 PID 后台动作、marker-based `InputArbiter`、前台 PID 前后校验、会话内不兼容动作熔断，以及默认关闭且 headless 失败关闭的旧 `computer` 前台兼容路径。后台仲裁会区分“用户在其它 App 操作”和“用户碰到目标窗口”：前者允许并行，后者立即中止；Event Tap 失效、事件记录不完整、锁屏或权限缺失均失败关闭。`/computer` 还会展示只存在当前进程内的路径/抢占/熔断计数，并直接显示自动前台回退恒为 0。

Phase 3 的独立浏览器 backend 与 Phase 4 的独立登录会话/VM 属于更高隔离等级的可选 runner，不是本次桌面核心链路的隐式 fallback；在这些 runner 真正接入前，网页和不支持 AX 的自绘 GUI 会明确返回能力边界，绝不悄悄抢占用户桌面。Windows 本版本同样只保留稳定窗口观察和默认关闭的前台兼容边界。

## 1. 结论先行

当前实现的冲突不是阈值参数问题，而是执行模型问题：`xcap` 截取的是用户当前图形会话，`enigo` 向同一会话的全局 HID 事件流注入鼠标/键盘。Agent 与用户共享同一个鼠标指针、键盘焦点、前台 App 和窗口状态，所以只要继续把“全局桌面注入”当作默认能力，就不可能同时满足以下四项：

1. 用户可以继续操作自己的 App；
2. Agent 操作另一个 App；
3. 双方的输入绝不串到对方窗口；
4. 用户看不到光标跳动、焦点切换或确认弹窗。

现有“礼让机制”（动作前读取 `idle_secs`，怀疑用户刚输入时暂停确认）只能降低碰撞概率，不能根治。推荐方案是把 computer-use 拆成两条执行路径：

- **默认路径：后台目标化执行**。操作绑定到稳定的 `WindowTarget(window_id, pid)`；截图按窗口获取；点击/输入优先走 macOS Accessibility 语义动作和目标进程事件，不改变系统前台 App 与物理鼠标位置。
- **兼容路径：前台接管**。保留现有全局 `enigo` 能力，但默认禁止自动降级；只有用户明确开启接管模式后才能使用，并受精确输入归因、可抢占 lease、目标窗口校验和现场恢复保护。

对于不支持后台目标化操作的 Canvas、游戏、自绘控件或受保护窗口，默认返回 `requires_foreground_takeover` 或排队等待，不能为了“任务成功率”悄悄切回全局输入。严格的“无感知”优先级必须高于覆盖所有 App。

## 2. 当前链路与根因

### 2.1 当前执行链路

```text
模型 computer tool call
        │
        ▼
ComputerTool::run
        │
        ├─ screenshot/zoom ──> xcap 主屏截图
        │
        └─ click/type/key/... ──> enigo ──> CGEventPost(HID)
                                             │
                                             ▼
                                   用户当前 GUI 会话的全局输入流
```

这条链路没有“目标窗口”“目标进程”“独立指针”“自动化会话”抽象。`click(x, y)` 会先把真实光标移动到坐标再点击；`type/key` 发给执行瞬间的前台焦点；用户只要在检查之后切换窗口，输入就可能落入错误 App。

### 2.2 已确认的八个根因

#### 根因 A：共享全局鼠标和键盘焦点

`crates/computer/src/backend.rs` 的 `click`、`double_click`、`scroll` 都先调用 `move_mouse`；键盘输入没有目标 PID，只依赖系统当前焦点。用户操作和 Agent 操作天然争用同一资源。

#### 根因 B：动作前检查存在 TOCTOU 竞态

当前活跃度检查发生在变更动作之前。检查通过到 `enigo` 真正发事件之间，用户仍可能移动鼠标、按键或切换窗口。`drag`、组合键和长文本输入期间也没有持续抢占检查。

#### 根因 C：`idle_secs + 宽限期` 不是可靠归因

现有实现用“距自身上次动作不足 0.8 秒”推断最新输入来自 Agent。这个窗口内如果用户也真实输入，会被错误归因成 Agent 自己，恰好形成最危险的漏判区。

更关键的是，项目使用的 `enigo 0.6.1` 已经给 macOS 合成事件写入 `kCGEventSourceUserData`，默认 marker 为 `100`；Windows 也提供 `dwExtraInfo` marker。系统 API 本来提供了精确区分自身事件与外部事件的基础，不应继续依赖时间猜测。

#### 根因 D：用户“正在看”无法由空闲时间识别

用户可能正在阅读屏幕但没有输入。此时 `idle_secs` 很大，Agent 仍会切 App、移动鼠标、改变页面，用户可以明显感知。提高或降低阈值都解决不了被动观看场景。

#### 根因 E：暂停确认本身就是打扰

当前 TUI 在检测到活动时显示 `ComputerUsePaused` 面板并等待 y/n。它避免了一部分误操作，却与“用户无感知”目标直接冲突；若用户正在别的 App，甚至可能看不到终端里的确认面板。

#### 根因 F：headless 默认继续，保护语义不一致

`ToolCtx::confirm_resume` 在没有 TUI sender 时直接返回 `true`。因此同样一次活跃度检测，在 TUI 会暂停，在 headless/部分自动任务路径会继续。安全策略不应取决于是否能显示 UI。

#### 根因 G：截图与动作没有绑定同一个稳定目标

全屏截图只代表某个时刻的桌面；模型推理期间，用户可以移动窗口、切 Space、打开遮挡层或改变焦点。动作执行前没有验证“截图中的目标窗口仍是同一个 window_id/pid、位置仍一致”。

当前新增的 `window_capture(query)` 已经向正确方向迈出一步，但它按标题/App 子串取第一个匹配窗口，结果没有把稳定的 window id、pid、bounds、capture generation 暴露给后续动作，仍无法形成安全的 observe-act 闭环。

#### 根因 H：同一 GUI 会话不存在通用的“第二套隐形桌面输入”

macOS 的 Space/虚拟桌面仍共享前台焦点和物理指针；仅把 App 放到另一个 Space 不能形成输入隔离。要对任意 GUI 做严格隔离，只能使用独立登录会话、虚拟机/远程桌面或应用自身提供的独立自动化通道。

## 3. 方案评估

| 方案 | 光标不跳 | 不抢焦点 | 用户输入不串窗 | 覆盖任意 App | 结论 |
|---|---:|---:|---:|---:|---|
| 调大 idle 阈值 | 否 | 否 | 否 | 是 | 只改变误报/漏报比例，不采用 |
| 动作后恢复光标 | 部分 | 否 | 否 | 是 | 只能减轻视觉干扰，作为兼容路径补丁 |
| Event Tap 精确归因与抢占 | 否 | 否 | 大幅改善 | 是 | 必须做，但它是安全层，不是无感知执行层 |
| `CGEventPostToPid` 目标进程事件 | 是 | 通常是 | 大幅改善 | 否 | 作为后台键盘/事件 fallback，需兼容矩阵 |
| macOS Accessibility (`AXPress`/`AXValue`) | 是 | 通常是 | 是 | 否 | 推荐的桌面后台主路径 |
| 按窗口后台截图 | 是 | 是 | 是 | 只读覆盖高 | 推荐的观察主路径 |
| Playwright/CDP 独立浏览器上下文 | 是 | 是 | 是 | 浏览器内高 | 浏览器任务推荐路径 |
| 独立登录会话/VM | 是 | 是 | 是 | 高 | 唯一通用强隔离，作为高级模式 |

`CGEventPostToPid` 和 Accessibility 都不能承诺所有 App 绝对不激活自身窗口；应用收到动作后也可能主动弹窗。因此每次后台动作都必须校验前台 PID 未改变，若改变则立即停止该 backend，并把该 App/动作记录为不兼容，而不是继续执行。

## 4. 推荐架构：Background First + Explicit Takeover

```text
                    ┌──────────────────────────┐
模型工具调用 ──────>│ ComputerRouter           │
                    └────────────┬─────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
      Window Observation   Background Action   Foreground Takeover
      xcap by window_id    AX / PostToPid      legacy enigo
              │                  │                  │
              └──────────> WindowTarget <──────────┘
                                 │
                                 ▼
                         InputArbiter / Guard
```

### 4.1 `WindowTarget`：所有动作必须绑定目标

新增稳定目标结构，禁止只靠标题字符串或裸坐标连续操作：

```rust
struct WindowTarget {
    window_id: u32,
    pid: u32,
    app_name: String,
    title: String,
    logical_bounds: Rect,
    capture_pixel_size: Size,
    target_size: Size,
    generation: u64,
}
```

- `window_list` 返回候选列表和稳定 id，不截图、不切前台。
- `window_capture(window_id)` 返回窗口图像以及上述 metadata。
- 后续每个动作携带 `window_id + generation`；执行前重新枚举并验证 pid、bounds 和窗口存活状态。
- 坐标以窗口截图左上角为原点，先换算到窗口逻辑坐标，再解析 Accessibility element；不再默认使用主屏全局坐标。
- 标题仅用于首次发现，不能作为连续动作的身份标识。

### 4.2 `app_computer`：新增 custom 后台工具

Anthropic 原生 `computer_20251124` 的 action schema 不能扩展 window id，因此不要硬改原生工具。新增普通 custom 工具 `app_computer`，并在系统提示中要求模型优先使用它；现有 `computer` 明确标记为 foreground compatibility tool。

建议动作：

- `list_windows`
- `screenshot`
- `click`
- `set_text`
- `key`
- `scroll`
- `inspect_element`

推荐执行顺序：

1. `click`：坐标映射到目标 App 的 AX element，优先 `AXUIElementPerformAction(kAXPressAction)`；不移动物理鼠标。
2. `set_text`：优先设置 `kAXValueAttribute` 或 `kAXSelectedTextAttribute`；避免逐字符写入全局键盘流。
3. `scroll`：优先对滚动条/滚动区域执行 AX increment/decrement 或设置 value。
4. `key`：没有等价 AX action 时，尝试带 wyj-code 专用 marker 的 `CGEventPostToPid(pid, event)`；动作前后验证 frontmost PID 没变。
5. 控件不支持 AX、目标不唯一或后台事件无效：返回结构化 `requires_foreground_takeover`，不自动使用 `enigo`。

### 4.3 `InputArbiter`：精确归因、用户绝对优先

无论后台路径还是兼容接管路径，都引入进程级 `InputArbiter`：

- macOS 使用 session-level listen-only `CGEventTap` 监听鼠标、滚轮和键盘事件。
- wyj-code 创建 `Enigo`/`CGEvent` 时使用专用 64-bit marker，不能继续依赖 enigo 公共默认值 `100`，避免与其他使用 enigo 的程序撞 marker。
- Event Tap 读取 `kCGEventSourceUserData`：marker 等于本进程值的是自身事件，其余视为外部输入。
- Windows 对应使用 low-level mouse/keyboard hook，结合 injected flag 和 `dwExtraInfo` marker。
- 维护 `external_event_seq`、`last_external_event_at`、`lease_generation`；不再维护 `last_own_input_at + grace_secs` 猜测。
- 用户事件一到达就 revoke 当前 foreground lease。后续合成事件在发送前检查 generation；长文本按小批次发送，每批之间检查；拖拽确保异常路径释放鼠标键。
- 后台目标化动作不因用户在其它 App 输入而全局暂停：仲裁器保留最近外部事件的类型与全局坐标，键盘事件只在目标已处于前台时冲突，点击/拖拽/滚动只在落入目标窗口区域时冲突；事件历史溢出或 Tap 短暂失效时仍失败关闭。
- Event Tap/Hook 初始化失败时，foreground takeover 必须 fail-closed；不能因为 headless 没有确认 UI 就继续。

注意：Event Tap 的作用是防碰撞和快速抢占，不能让全局输入变成“不可见”。它不能替代后台执行面。

### 4.4 前台接管必须成为显式模式

建议配置：

```toml
[computer_use]
mode = "background_first"          # 默认
foreground_fallback = "disabled"   # disabled | ask | idle_only
quiet_period_ms = 2000
max_defer_secs = 30
restore_context = true
```

行为定义：

- `disabled`：后台路径无法执行时直接返回 `requires_foreground_takeover`。
- `ask`：只在用户主动发起的交互会话中请求一次“本任务允许接管”，不是每个动作弹一次。
- `idle_only`：只有屏幕未锁定、持续静默达到 quiet period 且目标任务来自用户已授权会话时才接管；一旦出现真实输入立即撤销。
- schedule/headless 默认只能使用后台路径；不得把“没有 UI”解释为授权继续全局输入。
- 交互式工具权限按项目确认一次：`computer` 与 `app_computer` 首次批准（y/Enter/a）后分别写入 `~/.wyj-code/projects/<project_key>/allowed_tools.json`；同项目当前会话与重启后不再弹窗，不同项目隔离，拒绝不持久化。两种工具不互相隐式授权，避免后台批准扩大为旧前台全局输入权限。

接管现场恢复：

1. 记录原 frontmost pid、window id、光标位置和已按下的修饰键状态；
2. 每个动作验证目标窗口身份与 frontmost pid；
3. 用户输入到达后停止发新事件；
4. `Drop`/错误/取消路径释放所有由 Agent 按下的键和鼠标键；
5. 任务结束后恢复光标与原前台 App；若恢复会造成二次打扰，优先保持用户最新真实输入后的现场。

### 4.5 浏览器任务单独路由

网页操作不应继续占用桌面 GUI。增加 Browser backend（Playwright/CDP 或外部 MCP）并使用独立 browser context/profile：

- 不操作用户正在使用的浏览器窗口；
- 复用登录状态时使用显式导入/授权，不直接争用正在运行的 profile lock；
- 截图、点击、输入都在离屏页面内完成；
- 只有需要系统文件选择器、硬件密钥、验证码等边界场景才返回接管请求。

### 4.6 严格隔离模式

对自绘 GUI、远程桌面、游戏、受保护内容等无法后台目标化的应用，只有独立登录会话或 VM 能提供通用隔离。它不应成为默认安装负担，但可以作为高级 runner：

- 独立桌面、独立指针、独立焦点；
- 通过远程截图/输入协议驱动；
- 与用户主会话用文件/通知通道交换结果；
- 登录态、钥匙串和系统权限需单独配置，这是强隔离的真实成本。

## 5. 用户体验设计

默认体验不应再出现“检测到用户活动，是否继续”的动作级弹窗。

状态只需在 TUI 状态栏/工具结果里安静呈现：

- `后台操作 · TextEdit`：正在使用无干扰后台路径；
- `等待空闲 · 12s`：仅在用户允许 idle-only 接管时展示，不抢输入焦点；
- `需要接管`：后台能力不足，等待用户主动批准一次；
- `用户已接管`：真实输入触发撤销，Agent 停止并保留任务上下文。

模型收到 `requires_foreground_takeover` 或 `preempted_by_user` 后必须停下并向用户简短说明，禁止循环重试。

## 6. 分阶段实施

### Phase 0：把现有礼让机制升级为可靠安全层

1. 为 wyj-code 输入事件设置进程专用 marker。
2. 引入 passive Event Tap / Windows hook，按 marker 精确归因外部输入。
3. 删除 `last_own_input_at + 0.8s grace` 主判断；保留系统 idle 只用于 monitor 启动前的初始基线和 schedule 的启动门控。
4. headless/schedule 的 foreground 路径 fail-closed。
5. 活跃时静默 defer，不弹动作级确认；超时返回结构化结果。
6. 动作执行前后校验 frontmost pid/window id，补齐键鼠释放 RAII。

这一阶段显著降低串输入风险，但仍不是“无感知”完成态。

### Phase 1：按窗口观察 + macOS AX 后台交互

1. 将现有 `window_capture(query)` 拆为 `window_list` + `window_capture(window_id)`，保留 query 作为首次发现助手。
2. 返回 pid、bounds、target size、generation。
3. 新增 `app_computer` custom tool。
4. 实现 AX element inspect、press、set value、selected text、increment/decrement。
5. 无 AX 能力时返回明确 capability error，绝不自动降级。

### Phase 2：目标进程事件与兼容矩阵

1. 实现 `CGEventPostToPid` 键盘 fallback 和必要的目标化事件。
2. 对 macOS 原生 App、Electron、Chromium、Office、常见聊天 App 建立动作兼容矩阵。
3. 每个 App/动作验证：frontmost pid 不变、cursor 不变、目标截图产生预期变化。
4. 不兼容组合持久化为本机 capability cache，避免每次重新试错打扰用户。

### Phase 3：浏览器隔离 backend

网页任务优先路由到 Playwright/CDP；桌面 computer-use 只处理真正需要本地 GUI 的部分。

### Phase 4：可选强隔离 runner

为需要任意 GUI 且必须零干扰的高级用户提供独立会话/VM runner。

## 7. 验收标准

### 默认后台路径

- 物理光标位移：`0 px`。
- 前台 App 切换次数：`0`。
- 向全局 HID 流发送的变更事件：`0`。
- 用户持续在终端输入时，字符只进入终端，不进入 Agent 目标 App。
- Agent 操作失败时不自动切换到 foreground backend。
- 目标窗口被关闭、移动、换 PID 或 generation 失效时，动作在注入前中止。

### 显式 foreground takeover

- 用户真实输入到达后，下一批合成事件发送前撤销 lease；抢占目标 `< 50ms` 或一个不可拆分原子动作边界。
- 键盘/鼠标键在成功、错误、ESC 取消、panic-safe guard drop 路径都能释放。
- 动作落点前验证 frontmost pid/window id；不匹配即 abort。
- 用户真实输入后的现场优先，不用“恢复旧现场”覆盖用户的新操作。

### 观测与回归

本地可见、零外发 telemetry：

- background/targeted/foreground backend 使用次数；
- `preempted_by_user`、`target_changed`、`requires_foreground_takeover` 次数；
- cursor displacement、frontmost change、lease revoke latency；
- 每个 App/动作的后台成功率与自动降级次数（目标值：自动降级恒为 0）。

## 8. 测试矩阵

1. 用户持续移动鼠标并在终端输入；Agent 后台操作另一个 App：光标、焦点、用户字符均不受影响。
2. 用户与 Agent 同时操作同一目标窗口：后台动作检测目标冲突并 defer/abort，不与用户争写。
3. 用户在动作检查后、事件发送前切换 App：generation/frontmost guard 拦截。
4. 用户在长文本输入中途介入：输入分批停止，修饰键全部释放。
5. Canvas/自绘控件：返回 `requires_foreground_takeover`，不产生全局事件。
6. headless/schedule 且用户活跃：只运行后台 backend；没有后台能力则 defer/skip。
7. Event Tap/Accessibility 权限缺失：默认 fail-closed，并由 `/computer` 诊断显示具体缺失能力。
8. 多显示器、Retina、窗口移动、最小化、跨 Space、窗口重建后 id 变化。
9. App 动作后主动抢前台：检测到 frontmost pid 变化，立即熔断该 backend/动作组合。
10. `computer`/`app_computer` 首次批准后同项目当前会话与重启均不再请求权限；另一个项目仍弹窗，拒绝不落盘。
11. 普通 Bash/Edit 的 AllowOnce 仍只影响单次调用，不因 computer-use 的项目级语义扩大授权。

## 9. 代码落点建议

```text
crates/computer/src/
  activity.rs          -> InputArbiter 信号源；精确 marker/event tap
  target.rs            -> WindowTarget 枚举、身份与 generation 校验
  accessibility.rs     -> macOS AX backend
  targeted_event.rs    -> CGEventPostToPid / Windows targeted fallback
  takeover.rs          -> foreground lease、现场保存/恢复、RAII
  backend.rs           -> 保留截图与 legacy enigo，逐步瘦身

crates/tools/src/
  app_computer.rs      -> 新 custom 后台工具
  window_capture.rs    -> 按 window_id 捕获并返回 metadata
  computer.rs          -> 明确降级为 foreground compatibility tool

crates/core/src/tool.rs
crates/tools/src/ctx.rs
  -> computer/app_computer 项目级首次批准持久化；结构化 defer/preempt 结果，不再动作级暂停确认
```

## 10. 最终决策

1. 不把当前 `idle_secs` 礼让弹窗定义为根治方案；它只能作为过渡保护。
2. 默认禁止从后台动作静默降级到全局 `enigo`。
3. 优先落地 `WindowTarget + app_computer + AX backend`，这是同一 GUI 会话里实现高比例无感知操作的核心。
4. 同步落地 marker-based `InputArbiter`，用于解决竞态、用户抢占和兼容接管安全。
5. 浏览器任务走隔离 browser backend；任意 GUI 的严格零干扰最终由独立会话/VM 提供。

只有把“是否占用用户桌面”提升为路由层的硬约束，而不是某次动作前的概率判断，computer-use 才能从“会礼让的桌面遥控器”变成真正可与人并行工作的后台 Agent。

## 11. 调研证据与验证边界

本次结论来自当前仓库代码、锁定依赖源码和本机 macOS SDK，不依赖对外部能力的猜测：

- `enigo 0.6.1` 的 `Settings` 明确提供 `event_source_user_data`（macOS）和 `windows_dw_extra_info`（Windows）；默认 `EVENT_MARKER = 100`。
- `enigo` macOS backend 在 mouse move、mouse button、scroll、keyboard 等事件上写入 `EVENT_SOURCE_USER_DATA`，随后用 HID Event Tap 发布。因此当前“只能用时间猜自身事件”的前提不成立。
- Apple `CGEventTypes.h` 定义了 `kCGEventSourceUserData`；`CGEvent.h` 提供 listen-only Event Tap、`CGEventGetIntegerValueField` 和 `CGEventPostToPid`。
- Apple `AXUIElement.h` 提供 `AXUIElementCopyElementAtPosition`、`AXUIElementPerformAction`、`AXUIElementSetAttributeValue`；其旧的定向键盘 API 文档也明确区分“发送给指定 application”和“发送给 active application”，证明目标化输入是系统支持的设计方向。
- 当前锁定的 `xcap 0.9.6` 已能取得 `Window::id/pid/x/y/width/height/is_focused` 并按单窗口截图，足以构造 `WindowTarget` 的第一版，无需先替换截图依赖。

运行时验证边界：尝试用临时 Swift listen-only Event Tap 做 1 秒零位移 marker 探针时，探针进程被本机 Accessibility/TCC 卡在监听初始化，未得到回调结果并已主动终止；没有产生点击或可见光标移动。因此 Phase 0 仍需使用已经授予辅助功能权限的最终 `wyj-code` 二进制完成以下真机验收：自身 marker 可观测、真实输入 marker 不同、用户事件能撤销 lease、Event Tap 被系统禁用后能 fail-closed/re-enable。API 存在性和 enigo 写 marker 的事实已由源码确认，不能把尚未完成的 TCC 真机探针表述成已验证通过。
