# wyj-code v1.3.3 计划与实施记录

> 状态：**已实施**（相对 `v1.3.2` tag 之后、尚未打 tag 发布的全部改动：`/schedule` 定时任务系统 / `/import` 一键导入 Codex・Claude Code 配置 / 项目级配置目录 `.wyj/` → `.wyj-code/` 重命名 / Todo・子 Agent 详情面板滚动上限修复 / 列表选中态背景色统一为深灰）。五项改动分属不同会话并行完成，本文档在提交前统一归档。

## 一、新增：`/schedule` 定时任务系统

### 目标

让用户能通过 `/schedule` 面板管理一批"到点自动触发"的任务——一句话 prompt（如"每天 8 点抓取 AI 新闻并总结"），或把当前正在做的一件事固化成可重复执行的模板（如"每天 20 点做 A 股复盘、候选池筛选与跟进剔除"）。

### 架构决策

wyj-code 本身**没有常驻后台进程**（`-p` 单次执行完就退出，全仓库搜索 `cron`/`daemon`/`scheduler` 此前零命中），因此定时能力完全依赖系统级 `crontab`（v1 仅 macOS/Linux，Windows 面板可管理任务但同步动作报不支持）唤起 headless 执行；执行上下文为全新 headless 会话（非 `--resume` 累积同一 session）；每个任务独立绑定 `cwd`；跨天业务状态（如候选池）不由框架管理，完全交给任务 prompt 自己指导 Agent 读写用户指定文件；失败不重试，只记录 + 可选 macOS 系统通知；面板保存立即自动同步系统 crontab。

### 实施记录

- **数据层**（`crates/store/src/schedule.rs`，新文件）：`ScheduleTask{id, name, prompt, cron(标准 5 段), cwd, enabled, notify_on_failure, created_at, updated_at, last_run}` 落 `~/.wyj-code/schedule/tasks.json`（全局单文件，任务各自携带 `cwd` 字段区分归属，类比 `SessionFile.cwd` 的字段过滤模式而非物理分项目目录），原子写（临时文件 + rename，与 `lockfile.rs` 同款）。CRUD：`load`/`save`/`create_task`/`update_task`/`delete_task`/`set_enabled`/`record_run_start`/`record_run_result`，公开 API 均为绑定真实 `config_dir()` 的薄封装，内部真正实现按 `path: &Path` 参数化（`create_task_at`/`update_task_at`/`delete_task_at`），供单测注入临时目录，不触碰真实 `~/.wyj-code`。9 个单测覆盖 round-trip、唯一 id 生成、CRUD+run-record 全流程、缺失任务报错。
- **cron 表达式层**（`crates/store/src/cron_sync.rs`，新文件；唯一新增第三方依赖 `cron = "0.17"`）：`frequency_to_cron` 把"每天/每小时/每周+自定义"频率预设转成标准 5 段表达式；`cron` crate（zslayton/cron）要求 6/7 段（多一个秒字段，年可选）与系统 crontab 实际认的 5 段格式不同——持久化/系统 crontab 全程只用 5 段，仅在调用 `cron` crate 解析/算下次触发时临时转换（`to_cron_crate_expr` 补 `"0 "` 前缀 + `" *"` 年通配符），避免格式混淆污染存储层。`validate_cron`/`next_run_after` 供面板校验与"下次运行"展示。
- **crontab 同步**（同文件）：`sync_crontab` 只替换 `crontab -l` 输出里 `# BEGIN/END wyj-code schedule` 标记的区块，标记外内容原样保留；首次同步前自动备份原始 crontab 到 `schedule/crontab.backup.<ts>`（用 marker 文件保证只备份一次）；系统 `crontab` 读写抽在 `CrontabIo` trait 后面（`SystemCrontabIo` 真实实现 + 单测假实现），11 个单测覆盖频率生成、cron 校验、下次触发计算、"只替换标记块不动其他行"这一安全边界、禁用任务不产生空块、备份只发生一次。
- **触发执行层**（`wyj-code schedule run <id>`，`crates/cli/src/schedule_cmd.rs` 新文件）：**不复用** `main()` 里 `-p` 模式那段已与 TUI 深度耦合的 ~650 行 Agent/Provider 装配逻辑，而是用 `tokio::process::Command` 以子进程方式调用 wyj-code **自身二进制**的 `-p "<prompt>" --cwd <dir>` 入口——与用户手动 crontab 一条 `wyj-code -p "..."` 完全等价，零风险改动现有 headless 路径，且可独立测试。stdout/stderr 重定向到 `schedule/logs/<task-id>/<ts>.log`；成功后用 `SessionStore::last_for_project(cwd)` 反查最新落盘 session 关联进 `last_run.session_id`；失败记录错误摘要（日志尾部截断至 4000 字节）并按 `notify_on_failure` 开关走 macOS `osascript display notification`（其它平台 no-op，日志提示不支持）。CLI 子命令还提供 `list/add/remove/enable/disable/sync`，均支持 `--json`，除 `run` 外的写操作统一走 `sync_and_warn()`（crontab 同步失败只警告，不让整条命令失败退出）。
- **TUI 面板**（`tui::app::ScheduleDialog`/`ScheduleOverlay`/`ScheduleRow`/`ScheduleMenuAction` 等，`/schedule` 无参触发）：架构对齐 `ProfileDialog`（`/model`）而非 Mcp/Skills/Plugins 那套"每个动作立即生效"模型——批量编辑，`Ctrl+S`/Esc 三选一确认才真正 `schedule::save()` 整份 manifest + `cron_sync::sync_crontab()`；crontab 同步失败不回滚已落盘的任务数据，只转入 `ScheduleOverlay::SyncError` 停留在面板提示重试。字段编辑统一先弹小菜单再决定是否借用底部输入框（新增 `InputOwner::Schedule` 变体），比 Profile 对不同字段类型各自特判更简单：Cron 字段的菜单是"每天/每小时/每周/自定义"四选一频率预设，选中后进入对应的结构化短文本录入（如 `HH:MM`）而非直接裸写 cron 表达式。`AddNew` 行菜单额外提供"从当前对话固化为模板"——把会话里最近一条用户消息文本预填进新任务 prompt 草稿（不复制整段历史，避免 prompt 无限膨胀）。面板内"立即运行一次"与 cron 触发走同一条路径：`tokio::spawn` 异步 shell 出 `wyj-code schedule run <id>` 子进程，不在 TUI 进程内重新装配 Agent；仅对"已保存、未脏"的任务开放（脏态下菜单项 disabled）。渲染函数 `draw_schedule_dialog` 复用了三个已经与 Profile 无关的通用浮层绘制函数（`draw_action_menu`/`draw_profile_list_overlay`/`draw_profile_text_overlay`），未新增浮层绘制代码。
- **Slash 命令 + i18n**：`CommandResult` 新增 `OpenScheduleDialog`；`ScheduleCmd` 注册进两处 `standard_registry*`；headless 模式对应打印 `schedule.headless_unsupported` 提示；`help.body` 追加一行（CLAUDE.md 硬性约定）；`schedule:` 命名空间中英文各新增 40+ key（含 `dialog.input_owner.schedule_*` 系列）。
- **CLAUDE.md**：Architecture 编号列表追加第 13 条，说明"无常驻后台进程 + 系统 crontab 唤起子进程"这一核心架构约束，以及两条教训（cron 表达式 5 段 vs 7 段的转换边界、`crontab` 命令按 OS 用户而非 `$HOME` 隔离——手测时用假 `$HOME` 只隔离得了配置目录，真实 `crontab -l/-` 调用仍读写当前登录用户的系统 crontab，本功能开发期间的一次手动 E2E 冒烟测试就因此真实碰过一次系统 crontab，靠"只替换标记区块"的安全边界 + 事后 `schedule remove` 验证未造成影响）。

### 已明确保留的边界

- v1 仅 macOS/Linux 自动同步 crontab；Windows 面板可管理任务，同步动作显式报错提示"暂不支持，请用任务计划程序自行调用 `wyj-code schedule run <id>`"。
- 失败不自动重试；跨天业务状态（候选池等）不做框架层抽象，完全交给任务 prompt 自己读写文件。
- Prompt 字段按单行文本编辑（复用现有 `InputOwner` 提交式录入机制，Enter 即提交），未做多行富文本编辑器；日常够用的单句 prompt 场景已覆盖。
- 面板"立即运行一次"只对已保存任务生效（脏态需先保存），不支持"预览未保存改动的执行效果"。

## 四、修复：Todo / 子 Agent 详情面板滚动上限计算错误

### 现象

Todo 详情面板 / 子 Agent 详情面板内容较短、完全在可视区域内时，PageUp/PageDown 应该穿透到聊天区滚动，但此前会被详情面板的滚动逻辑吞掉（按键无效果，也不滚动聊天区）。

### 根因与修复

`app::AppState::scroll_focus_lines`（`crates/tui/src/app.rs`）在 `UiFocus::Todos`/`UiFocus::SubAgents` 且详情面板展开时，靠 `Self::adjust_bounded_u16_scroll(&mut scroll, delta, max_scroll)` 的返回值（是否真的在边界内移动了）判断该在面板内滚动还是穿透给 `scroll_chat_lines`；这个判断完全依赖 `todo_detail_max_scroll`/`sub_agent_detail_max_scroll` 与当前渲染出的真实内容行数保持同步。此前渲染函数（`render::push_inline_todo_lines` → `push_todo_detail_lines`，子 Agent 侧同构）只接收滚动 offset 作为参数、不回传该次渲染实际算出的内容行数上限，导致 state 里的 `*_detail_max_scroll` 可能与当前渲染内容不同步（尤其内容变短后 max_scroll 未跟着降为 0），键位路由因此误判"面板内还有滚动空间"。

修复：两个详情渲染函数改为返回 `(next_scroll, next_max_scroll)` 二元组，渲染时就地算出的真实内容行数立即回写 `state.todo_detail_max_scroll`/`state.sub_agent_detail_max_scroll`（`render.rs` 对应调用点解构使用），`scroll_focus_lines` 的路由判断从此和实际渲染内容保持同步。新增 5 个单测：`todo_detail_scroll_falls_back_to_chat_when_content_fits_viewport`、`todo_detail_scroll_stays_internal_when_room_remains`、`sub_agent_detail_scroll_falls_back_to_chat_when_content_fits_viewport`、`sub_agent_detail_scroll_stays_internal_when_room_remains`、`rendering_short_todo_detail_writes_back_zero_max_scroll`。

## 五、UI：列表选中态背景色统一为深灰

### 起因

用户要求把 Todo 列表和 Agents 列表里"当前选中项"的背景色改成深灰色，更方便辨识。

### 盘点发现的深层问题

在动手改这两处之前先盘点了全应用现有的"选中行"样式，发现实际上混用了三套不一致的视觉语言，这本身就是"不好辨认"的根源之一：

1. **饱和蓝色背景**（`Color::Blue`）：Todo 列表（`push_inline_todo_lines` 的 `selected_style` 闭包）、子 Agent 聚合面板（`draw_sub_agents_panel` 的 `sel_bg` 闭包）、会话选择器（`draw_session_picker`）、斜杠命令补全弹窗（`draw_slash_completions`，name/desc 两个 Span 各一处）。
2. **完全没有背景色，只靠文字颜色 + 加粗 + 前缀箭头**（`Style::default().fg(Theme::CLAUDE).add_modifier(Modifier::BOLD)`）：`draw_settings_dialog`、`draw_memory_dialog`、`draw_mcp_dialog`、`draw_skills_dialog`、`draw_plugins_dialog`、`draw_agents_dialog`、`draw_extensions_dialog`、`draw_import_dialog`，以及 `draw_profile_dialog`/`draw_schedule_dialog` 里 `selected_row` 分支（这两个额外有一个语义不同的 `editing` 分支：黑字橙底，表示"正在编辑，见下方输入框"，不属于本次改动范围，未触碰）——这 10 处的选中态样式代码**逐字节完全相同**，是典型的可提炼共享样式却各自复制粘贴的情况。
3. **`Color::DarkGray`**：聊天区消息选中（Ctrl+O 展开），`render_thinking_block`/`render_chat_message`/`render_message_range` 三处。

用户要求的 Todo 列表属于第①类，Agents 列表属于第②类。征求用户意见后，选择**全面统一**而非只改这两处。

### 实施

- `crates/tui/src/theme.rs` 新增 `Theme::SELECTED_BG: Color = Color::Rgb(66, 66, 66)`（中深灰，与已有 `STATUS_BG = Rgb(30,30,30)` 拉开足够对比度，跟应用其余颜色一样用 RGB 精确值而非终端调色板色名，保证跨终端一致）+ `Theme::selected_row() -> Style`（`fg(CLAUDE) + bg(SELECTED_BG) + BOLD`，品牌橙前景在深灰底上保持可读性和一致的"这是強调色"语义）。
- 第②类 10 处：`Style::default().fg(Theme::CLAUDE).add_modifier(Modifier::BOLD)` 原地替换为 `Theme::selected_row()`（用 Python 脚本按精确锚点行定位替换，避免误伤同样用 `fg(CLAUDE)+BOLD` 但语义是"对话框标题"而非"选中行"的其它代码）。
- 第①类 5 处：`bg(Color::Blue)` 替换为 `bg(Theme::SELECTED_BG)`，其余已搭配好的前景色（`Color::White` 加粗名称、`Color::Rgb(180,200,255)` 浅蓝描述文字等）原样保留——只统一背景，不重新设计每处的前景配色方案。
- 第③类（聊天消息选中的 `Color::DarkGray`）未改动：语义上是"消息级选中"而非"列表行选中"，且已经是深灰，不在本次"不一致"问题范围内。

### 效果

全应用所有列表/管理面板（Todo、子 Agent 面板、会话选择器、斜杠命令补全、Profile/Mcp/Skills/Plugins/Extensions/Import/Schedule/Agents/Settings/Memory）的"当前选中行"现在统一为同一种深灰底+橙字+加粗的视觉语言，不再有的饱和蓝、有的无背景色的不一致观感。
