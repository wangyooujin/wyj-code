# wyj-code v1.3.0 计划与实施记录：Computer-Use（桌面 GUI 控制）

> 状态：**已实施**（API 层 / `wyj-computer` crate / `ComputerTool` 原生+custom 双模式 / 会话内放行权限 / 注册门控 / `zoom` 识别准确率增强 / held 修饰键点击 / `/computer` 诊断命令 / 模型误拒"读应用内消息"类请求的提示修复 / 文档，见下方「实施记录」）。TCC/DPI preflight（应用启动时主动引导授权，区别于 `/computer` 的按需诊断）未实施（保留边界），真机端到端手测仍待用户执行（见「验证」）。

## 实施记录

- **API 层**（`crates/api/src/types.rs`、`crates/api/src/anthropic.rs`、`crates/api/src/openai.rs`）：`ToolDefinition` 新增 `native: Option<NativeToolSpec>`（`tool_type`/`extra`/`beta` 三字段，`beta` 为 `String` 而非 `&'static str`——`Deserialize` 派生要求所有字段生命周期非 `'static` 绑定）；`build_api_tool()` 按 `native` 是否为 `Some` 分支序列化，`ApiRequest.tools` 类型由 `Vec<ApiTool>` 改为 `Vec<serde_json::Value>`；`collect_beta_header()` 独立成可单测的纯函数，遍历工具收集去重后的 `native.beta`。全仓 ~18 处既有 `ToolDefinition { .. }` 构造点机械补齐 `native: None`。OpenAI provider 过滤掉 `native.is_some()` 的工具（防御性，实际只在 Anthropic profile 下才会注册）。新增 6 个单测覆盖序列化线格式与 beta header 去重。
- **`crates/computer`（`wyj-computer`）**：未按原计划手写 macOS/Windows 两套 backend——`xcap`（截图）与 `enigo`（输入合成）自身已按 target_os 内部分派，因此只写了**一份** `backend.rs`（`#[cfg(any(target_os = "macos", target_os = "windows"))]`）+ 一份 `unsupported.rs` 桩实现（其余平台，含 Linux）。依赖锁定版本：`xcap = "0.9"`（0.0.x 系列与当前 core-foundation/objc2 生态有类型推断编译错误，已弃用）、`enigo = "0.6"`。`scale` 模块（`fit_within`/`CoordScaler::{to_physical,to_target}`）平台无关、13 个单测全覆盖（含四角落/越界钳制）。`Capture::png_base64()`/`coord_scaler()` 便捷方法。
- **`ComputerTool`**（`crates/tools/src/computer.rs`，`#[cfg(any(target_os = "macos", target_os = "windows"))]`）：11 种 action（screenshot/cursor_position/wait/mouse_move/left_click/right_click/middle_click/double_click/left_click_drag/key/type/scroll）手动按 `action` 字段分派（未用 serde 内部标签枚举，为的是未识别 action 能给出清晰错误而不是笼统的反序列化失败）。click 系动作的 `text`（held 修饰键）字段的支持见下方「增强四」（不再是"故意收窄范围"，已补齐）；`hold_key`/`triple_click` 等边缘 action 仍未支持。安全兜底两项：失控角判定 `in_dead_corner`（四角 5px 阈值）；连续动作计数**锚点从计划的「回合起点」改为「距上次 screenshot」**——`Tool` trait 无跨调用的回合边界钩子，改用「多久没截图核实」作为更贴切的节流信号，上限 20。18 个单测覆盖分支判定/坐标解析/摘要文案/native 工具定义。
- **会话内放行权限**（`crates/tools/src/ctx.rs`）：新增 `SESSION_SCOPED_TOOLS: &[&str] = &["computer"]` + `is_session_scoped_tool()`（后续新工具要复用同待遇只需加一行）、`ToolCtx.session_allowed: RwLock<HashSet<String>>`（不落盘）；`confirm_tool` 的 `AllowAlways` 分支按 `is_session_scoped_tool(name)` 二选一写入 `session_allowed` 或 `always_allowed`+`persist_allowed_tools()`。TUI 弹窗（`crates/tui/src/render.rs::draw_permission_dialog`）按同一判定选择 `dialog.permission_hint`/`dialog.permission_hint_session_scoped` 两条 i18n 文案（en/zh 均已补）。
- **注册门控**（**已被下方「增强」节的双模式取代**）：`cli::register_computer_tool_if_enabled(&mut registry, &cfg)`（`#[cfg]` 双实现，非目标平台是空函数，避免运行时 `cfg!()` 判断），在 `main.rs` 初始 `registry`（`-p`/`--headless`/TUI 共用同一构建路径）与 `/model` 重建闭包 `rebuild_fn` 两处调用；子 Agent 工厂 `make_sub_agent_factory` 不调用，子 Agent 默认不含 computer-use。最终门控条件（拆成两层判断，见下方「增强」节）：注册与否看 `profile.vision && provider == Anthropic`；用不用原生工具声明另看 `profile.is_official_anthropic_endpoint()`。
- **验证**：`cargo fmt --check` / `cargo check --workspace` / `cargo test --workspace`（440 个测试全绿，含新增的 API/wyj-computer/ComputerTool/ctx/config 单测，见下方增强三的 zoom 测试明细）/ `cargo clippy --workspace --all-targets -- -D warnings` 均在本机（macOS/darwin）跑绿。真实截图/输入合成/TCC 权限授权未做自动化验证（见下方「验证」节的手测清单，需真机交互执行）。

### 修复：门控误放行第三方 Anthropic 协议兼容端点（用户报告，MiniMax M2/M3）

首版门控只判断 `matches!(cfg.provider(), wyj_config::Provider::Anthropic)`。国内大模型（MiniMax/GLM/Kimi 等）常以 `provider = "anthropic"` + 自定义 `base_url` 接入 wyj-code——说的是 Anthropic Messages API 协议，但服务端不是 `api.anthropic.com`，不认识 Anthropic 专属的原生工具类型。这类 profile 一旦 `vision=true`，就会通过原有门控注册 `ComputerTool`，模型一调用（如"打开本地软件"触发 computer-use）就把 `computer_20251124` 原生工具定义发给 MiniMax 端点，返回 `400 invalid_request_error: invalid params, function...`，整轮对话失败。

根因：`provider == Anthropic` 只说明"按 Anthropic 协议格式序列化请求"，不能说明"服务端是官方 Anthropic 基础设施、认识专属扩展"。这个区分在本仓库其实早有先例——`Profile::effective_prompt_cache()`（`crates/config/src/lib.rs`）判断 prompt caching beta 是否默认开启时，本就检查了 `provider == Anthropic && (base_url 为空 || base_url == 官方地址)`，只是 computer-use 门控没有复用这个判定。

修复：把该判定提炼成 `Profile::is_official_anthropic_endpoint()` 公共方法（`crates/config/src/lib.rs`），`effective_prompt_cache()` 改为调用它（消除重复），`register_computer_tool_if_enabled` 改用它替换原来粗粒度的 provider 判断。新增单测 `is_official_anthropic_endpoint_distinguishes_real_api_from_compatible_proxies` 覆盖：空 `base_url`/官方地址 → true；第三方 `base_url`（含 MiniMax 域名）→ false；`provider = OpenAI` 即便 `base_url` 为空也 → false。

**此修复只解决了"不再 400"，用户随即指出这不是他们要的**——他们要的是 MiniMax M3 上 computer-use 真正可用，而不是被关掉。见下一节。

### 增强：原生/custom 双模式，让第三方 Anthropic 协议端点真正可用（用户第二轮要求）

用户明确诉求：不是"避免报错"，而是"MiniMax M3 也能正常使用 computer-use 功能"。上一节的修复把 `is_official_anthropic_endpoint() == false` 的 profile 整体排除在注册之外——规避了 400，但功能对这类用户彻底不可用，不满足需求。

深层原因：Anthropic 原生 `computer_20251124` 工具**没有 description/input_schema**，因为这个空 schema 的调用约定（有哪些 action、参数叫什么、坐标系是什么）是 Claude 在训练阶段习得的隐式知识，不是协议层能表达的信息。MiniMax M3 即使完整支持 Anthropic Messages API 协议（tool_result 内嵌 image block、custom 工具的 tool_use/tool_result 往返都没问题），也没有这层训练——发给它一个只有 `{type, name, display_width_px, display_height_px}` 的工具声明，它根本无从得知该怎么调用。这不是一个"协议兼容性"问题，是"训练数据"问题，光解决 400 不解决可用性。

解法：**`ComputerTool` 双模式**，`run()` 的动作分派逻辑两种模式完全一致，只有 `definition()` 的对外声明方式不同：
- `ComputerTool::new(max_dim, native: true)`（官方端点）：声明为原生 `computer_20251124` 工具，`native: Some(NativeToolSpec{...})`，不带 description/input_schema——依赖 Claude 的内置训练。
- `ComputerTool::new(max_dim, native: false)`（第三方 Anthropic 协议端点）：声明为**普通 custom 工具**，`native: None`，带完整 description（`descriptions::computer_custom_description(target_width, target_height)`——动态嵌入实际截图分辨率，逐条列出全部 11 种 action 的必填/可选字段、坐标系约定、"先截图再行动、行动后再截图核实"的工作流）+ 完整 input_schema（沿用原有 JSON schema，从"仅供本地展示"升级为"真正发给模型、被强制/引导遵循"）。custom 工具是标准协议概念，任何具备基本工具调用能力的模型都能正确使用，不依赖 Anthropic 专属训练。

门控相应拆成两层判断（`cli::register_computer_tool_if_enabled`）：
1. **注册与否**：`profile.vision && provider == Anthropic`。这里恢复成只看 provider（不再要求官方端点），因为截图回传给模型靠的是 Anthropic Messages API 协议本身的 tool_result 内嵌 image block 能力，MiniMax 的 Anthropic 协议端点一样具备——真正卡住功能的从来不是"是否官方"，而是"协议是否支持图片回传"。`provider == OpenAI` 时仍不注册：OpenAI Chat Completions 的 `tool` 角色消息不支持图片内容（`crates/api/src/openai.rs` 现状），截图会降级成纯文本占位符，模型看不到画面，注册了也是名存实亡（这是本次评估后明确的已知边界，未展开修复——若要支持需要在 Agent 循环层面把截图从 tool_result 挪到后续 user 消息里，改动更大，本次未做）。
2. **原生与否**：`profile.is_official_anthropic_endpoint()`（第一轮修复引入的判定）。只决定"用哪种工具声明格式"，不再决定"注册不注册"。

新增 3 个单测：`custom_mode_definition_has_no_native_spec_but_full_schema`、`custom_mode_description_embeds_actual_target_resolution`、`native_mode_description_is_display_only_placeholder`；`ComputerTool::new` 签名从 `(max_dim)` 变为 `(max_dim, native)`，全部既有调用点（生产代码 1 处 + 测试 4 处）同步更新。

### 增强二：系统提示教模型"打开应用用 Bash、动作确认自动发生"（用户第三轮反馈）

双模式修好之后，用户实测截图（MiniMax M3 走 custom 模式）：用户让它"打开同花顺看自选股"，模型调用 `computer` 截了一张图，看到的是终端桌面（同花顺没开），于是直接回复"我没看到同花顺窗口，请你先手动打开，或者告诉我'允许打开同花顺'，我再操作"——截了一次图就放弃了，没有尝试自己打开目标应用。

根因不是权限或协议，是**工作流知识缺口**：模型不知道 wyj-code 里 `Bash` 工具和 `computer` 工具是同时可用的，也不知道"打开一个应用"这件事用 Bash 一条命令（如 macOS `open -a "应用名"`）远比在 GUI 里翻找 Dock/Spotlight/开始菜单可靠；同时它把"操作电脑"这件事当成了需要用户在聊天里显式说"允许"的高风险操作，但实际上 wyj-code 的逐动作确认弹窗本来就会在每次 click/type/key 等变更动作执行前自动弹出——不需要模型先在聊天里问一遍。这两点原生模式下靠 Claude 的内置训练大概率不是问题，但 custom 模式（第三方模型）完全没有这层默认知识，必须显式告诉它。

解法：新增 `wyj_core::prompts::COMPUTER_USE_HINT`（`crates/core/src/prompts.rs`），复用现有的"模式追加提示"机制（`PLAN_MODE`/`NON_INTERACTIVE` 同款模式）——`register_computer_tool_if_enabled` 签名改为返回 `bool`（是否实际注册），`main.rs` 据此在 `agent` 构建后 `agent.append_system(COMPUTER_USE_HINT)` 并写入 `system_prompt_extra`（该变量已有的机制保证 `/model` 热切换重建 Agent 时原样拼回，无需额外改 `rebuild_fn`）。提示内容：打开应用优先用 Bash 直接启动；启动后等一下再截图确认；变更动作已有自动确认弹窗、不必先问用户"允许"。custom 模式下 `descriptions::computer_custom_description()` 里也复述了同样两点（工具描述本身可能比系统提示权重更高，双保险）。

这条提示是**通用的、不区分原生/custom 模式**都会追加——原生模式下 Claude 虽然认得 computer 工具本身，但"优先用 Bash 开应用"这类工作流偏好同样不在它的默认行为里，加上也有好处，成本可忽略。

### 增强三：`zoom` 动作提升识别准确率（用户第四轮反馈 + 网络调研）

用户反馈"图片识别错误率挺高"（模型读错自选股名称/价格等界面数据），要求调研网络最佳实践并落地。用 WebSearch 做了三组调研（Anthropic 官方 computer-use 最佳实践、GUI agent 截图定位准确率的学术研究、Set-of-Mark 提示法），结论：

- **Anthropic 官方博客**（[Best practices for computer and browser use with Claude](https://claude.com/blog/best-practices-for-computer-and-browser-use-with-claude)）：截图务必在发送前预先下采样（避免服务端二次缩放导致坐标错位）；1280x720 是大多数场景的安全默认分辨率（**印证了现有 `DEFAULT_MAX_DIM=1280` 本就是对的，不用改**）；把整张图切成小 tile 或叠加坐标网格**没有**改善点击准确率（结果验证了不该做 grid overlay）；`computer_20251124` 疑似存在 `enable_zoom` 一类的服务端放大机制，供 Claude 在文字太小时自动放大看——**这条经三次 WebFetch 尝试（`platform.claude.com`/`claude.com`/`github.com`）均被本环境的网络策略拦截，无法核实具体字段名，因此没有把这个未经证实的字段写进原生模式的 wire 请求**（治理原则：不对外部 API 打没验证过的猜测字段，尤其不能因为一次没验证的改动搞坏本来工作正常的官方路径）。
- **学术研究**（RegionFocus / UI-Zoomer / GUI-Eyes / AdaZoom-GUI，均 2025-2026）：测试时动态裁剪放大（crop-then-zoom）是目前提升 GUI grounding/OCR 准确率最有效、且**不需要额外训练**的技术，多个基准上有 +10~28 个百分点的量级提升；这类技术对没有 Claude 那层专属训练的第三方模型（如 MiniMax）尤其关键。
- **Set-of-Mark（画框编号）**：一度流行，但 Anthropic 自己的测试和更新的研究都显示效果有限甚至无提升，予以排除。

落地：**在自己完全掌控的 custom 工具 action 集合里新增 `zoom`**（而不是去猜官方原生字段），两种模式都能用（`run()` 分派不区分 native/custom）：
- `wyj-computer` 新增 `capture_region(x0,y0,x1,y1,max_dim)`：截主屏后裁剪到物理像素矩形，只有裁剪结果仍超过 `max_dim` 才下采样——多数"放大看细节"场景裁剪区域远小于 `max_dim`，因此有效分辨率远高于同一块内容在全屏缩略图里的样子。裁剪矩形的钳制逻辑抽成纯函数 `scale::clamp_region`（越界/颠倒都不 panic，退化到至少 1x1），4 个单测覆盖。
- `ComputerTool::do_zoom`：解析 `region: [x0,y0,x1,y1]`（目标坐标空间，与 `coordinate` 同一坐标系），四周加 12%（`ZOOM_PADDING_RATIO`）余量防止切边，映射到物理像素后调用 `capture_region`。归类为只读 action（`is_read_only_action` 新增 "zoom"），不需权限确认，且和 `screenshot` 一样重置连续动作计数（zoom 也是"核实现实"，不是盲跑）。
- Schema/描述同步：custom 模式 `input_schema` 加 `"zoom"` action + `region` 字段；`descriptions::computer_custom_description()` 与 `wyj_core::prompts::COMPUTER_USE_HINT` 都新增"读数字/密集文字前先 zoom，不要猜"的提示（后者是通用系统提示，前者是 custom 模式专属的工具描述，双保险，逻辑同增强二）。
- 新增 8 个单测：`clamp_region` 4 个（有效矩形/越界钳制/退化保护/边角）+ `ComputerTool` 侧 5 个（`required_region` 解析/校验、`do_zoom` 拒绝颠倒区域、`needs_permission` 为 zoom 返回 false、custom 模式 schema 含 zoom+region）。

**为什么没有同时提高 `DEFAULT_MAX_DIM`**：Anthropic 官方指导已经把 1280x720 定为大多数场景的推荐默认值，调研没有给出"应该更高"的证据，反而强调"别超限导致服务端二次缩放"；真正的瓶颈是"全屏缩略图里单个小区域的有效分辨率不够"，`zoom` 直接针对性解决这个瓶颈，比全局调高分辨率（更贵、且不解决问题——全屏分辨率再高，最终还是会被下采样到差不多的 token 预算）更精准。

### 增强四：held 修饰键点击 + `/computer` 诊断命令（补齐此前标注为"保留边界"的两项）

补齐规划文档里此前明确标注为"保留/未实现"的两处收尾工作，都不是用户新反馈，是主动补齐：

- **点击类动作的修饰键支持**（对齐 Anthropic 官方 computer-use 调用约定）：`left_click`/`right_click`/`middle_click`/`double_click` 复用与 `key` 动作相同的 `text` 字段传入要按住的修饰键组合（如 `"shift"`/`"cmd"`），用于 shift-click 多选、cmd-click 等场景。
  - `wyj-computer` 新增系统层原语 `key_down`/`key_up`（`backend.rs` 把原来的 `key()` 拆成 `parse_key_combo`（共享解析）+ `key_down`（仅按下）+ `key_up`（仅释放，按相反顺序），`key()` 现在就是 `key_down` 紧接 `key_up`）；非 macOS/Windows 的 `unsupported.rs` 桩同步补齐。按键按下/释放状态存在于操作系统层面而非某个 `Enigo` 实例，因此 `key_down` 与之后的一次鼠标点击、`key_up` 之间可以安全跨越多次独立调用。
  - `ComputerTool::do_click`：点击前 `key_down`（有 `text` 时），点击后无论成败都尝试 `key_up`，优先向模型报告点击本身的错误、`key_up` 失败作为次要错误兜底报告——避免修饰键状态残留（用户后续操作会莫名其妙触发 shift 效果）比"漏报一个次要错误"更值得优先规避。
  - `descriptions::computer_custom_description()` 补充 `text` 字段在点击动作上的用法说明；`summarize_action()` 权限确认弹窗摘要同步展示（如 `left_click at (10, 20) holding shift`）。新增 3 个单测覆盖摘要格式（有修饰键/无字段/空字符串三种输入）。
  - 原生模式（`native=true`）无需改动——这本来就是 Claude 训练时习得的官方调用约定的一部分，custom 模式此前没暴露对应的系统层原语才是真正的缺口。
- **`/computer` 诊断命令**（`commands::builtin::ComputerCmd`，注册在 `standard_registry()`/`standard_registry_with_skills()`）：只读诊断，不需要真的注册 `ComputerTool` 就能跑。`crates/commands` 新增对 `wyj-computer` 的直接依赖（不经 `wyj-tools`，保持 crate 依赖边界干净——诊断命令只需要系统层探测能力，不需要整个工具实现）。
  - 门控判断独立复现 `cli::register_computer_tool_if_enabled` 的逻辑（平台 → vision → provider），再用 `Profile::is_official_anthropic_endpoint()` 判断真实会用原生还是 custom 模式；平台受支持时额外做三项实时探测：`primary_display_size()` + `scale::fit_within()` 算出真实会用的目标分辨率、`capture_primary(64)` 真的截一张小图验证屏幕录制权限链路、`cursor_location()` 验证辅助功能权限链路可达。
  - 固定附带一条 macOS 辅助功能提醒：`cursor_location()` 读取成功只代表这一次 API 调用没报错，**不代表**点击/按键会真的生效——未授权辅助功能时 `Enigo::new()` 往往仍然成功，后续合成事件被系统静默丢弃且没有任何报错，这种失败模式无法通过"捕获错误"发现，只能靠固定文案提前告知用户去哪检查。
  - i18n key 前缀 `computer.*`（en/zh 均已补齐），`/help` 的 `help.body` 模板同步追加一行（CLAUDE.md 硬性约定）。

### 修复：模型误拒"帮我看看某 App 里的消息"类请求（用户第五轮反馈）

用户反馈：让 wyj-code 打开某聊天软件、查看某联系人发的消息，模型直接拒绝，理由是"我无法打开该软件或访问电脑上的应用程序——即便是 desktop 控制工具（computer）也需要通过 GUI 点击/键入操作，不是直接调用该软件的 API"，并补充"即便我能截屏，你登录的是你自己的账号，我看到的内容会包含你不想暴露的隐私信息"，转而建议用户自己手动打开软件查看。

诊断：这不是权限/协议层面的技术限制（computer-use 当时已正确注册，能截图/点击/输入），是模型的两个错误前提叠加导致的过度拒绝：

1. **误以为"读取应用内容"需要该应用的 API**：忽略了 screenshot/zoom 本身就是通用的"读屏幕上任何渲染内容"的手段，跟 `type`/`click` 一样是这个工具原本就该覆盖的用法，不需要为每个 App 单独接入 API。
2. **误把"用户自己的隐私"当成需要回避的第三方隐私**：这是用户自己的设备、自己已登录的账号，且是用户本人当场直接提出的请求——不存在"要不要暴露给谁"的问题，回避这一步反而是没有正确理解请求的授权边界。

修复：不改变权限模型本身（点击/输入类动作依然逐个走确认弹窗，这层安全机制没有变化，也是让"模型不必自己纠结"这个论点成立的前提），只在两处模型侧提示追加一段话把上面两个前提挑明：
- `wyj_core::prompts::COMPUTER_USE_HINT`（通用系统提示，两种模式都会看到）。
- `descriptions::COMPUTER_CUSTOM_TEMPLATE`（custom 模式专属工具描述，第三方模型没有 Claude 训练时习得的兜底认知，更需要这段话）。

内容要点：截图/zoom 读取聊天记录、邮件、通知等屏幕上渲染的任何文字不需要 API；这是用户自己的设备和账号、用户本人发起的请求，没有需要回避的第三方隐私；把这类请求当成用 screenshot/zoom 就能完成的普通任务去执行，而不是拒绝后让用户自己去看。全仓 `cargo fmt --check`/`cargo check --workspace`/`cargo test --workspace`/`cargo clippy --workspace --all-targets -- -D warnings` 均跑绿（纯字符串常量改动，无需新增测试）。

## 目标 / 背景

让 wyj-code 支持 Anthropic 官方 **computer-use** 能力：模型通过截图观察桌面、合成鼠标/键盘事件操控任意 GUI 应用，达到 Claude Code 级别的权限与 UX 打磨。

> 说明：Claude Code 本身不内置桌面控制；"computer-use" 特指 Anthropic 的 `computer_2025xxxx` 工具。"对标 Claude Code" 理解为**在 wyj-code 里实现该官方能力，并复用其成熟的权限/TUI 打磨风格**。

**现状体检（已核实，含行号）**
- 图片回传链路**已完备**：`ToolResult::with_parts` → `ToolResultPart::Image`(base64) → Anthropic 原生 `image` block。`Read` 读 png 已在用（`crates/tools/src/read.rs:80-117`）。截图工具照抄即可把画面发给模型，**零类型系统改动**。
- 逐调用权限确认**已完备**：`needs_permission` + `action_summary` + `ctx.confirm_tool` + 弹窗（`crates/core/src/agent.rs:768-775`、`crates/tools/src/ctx.rs:172-211`、`crates/tui/src/render.rs:2654-2687`）。
- vision 门控**已有**：`Profile.vision`，非 vision 时图片降级占位文本（`crates/api/src/anthropic.rs:278-321`）。
- 缺口：① 无系统级截图/输入合成依赖（无 xcap/enigo/screenshots/rdev）；② 终端无法显示截图（Inline viewport 纯文本、无 Sixel/Kitty），**仅模型可见像素**；③ OpenAI provider 丢弃 image block（`openai.rs:188`）→ 功能 Anthropic-only。

## 访谈结论（锁定的设计决策）

1. **控制目标**：桌面 GUI 控制（整机截图 + 鼠标 + 键盘）。
2. **接入方式**：Anthropic 原生 computer 工具（`computer_20251124` + `anthropic-beta: computer-use-2025-11-24`）。
3. **平台**：macOS + Windows（Linux 不在首版，构建需隔离）。
4. **权限**：截图放行（只读）+ 变更动作（click/type/key/scroll/drag）逐个确认。
5. **启用**：平台 + vision profile 自动启用；**细化叠加"真正的 Anthropic 官方端点"门控**（不能只判断 `provider == Anthropic`——MiniMax/GLM/Kimi 等第三方服务常以 `provider = "anthropic"` + 自定义 `base_url` 接入，需一并检查 `base_url`，见下方实施记录的修复说明），避免第三方 Anthropic 兼容端点收到 native computer 工具而 400。
6. **授权粒度**：会话内放行，不落盘（新增 `session_allowed`，不写 `allowed_tools.json`）。
7. **捕获范围**：仅主显示器。
8. **安全兜底**：ESC 中断 + 失控角（鼠标甩到屏角立即 abort）+ 单轮连续动作上限。

## 架构与关键改动

### A. 新增 crate `crates/computer`（`wyj-computer`）
平台无关的截图 + 输入合成层，两套 `#[cfg]` backend（macOS / Windows），Linux 编 stub。
- 公共 API：`capture_primary() -> Result<Capture>`（含 physical 尺寸 + PNG/RGBA）、`Input::{left_click,type_text,key,scroll,move,drag,double_click,right_click,...}`、`cursor_location() -> (i32,i32)`（失控角用）、`primary_display_size()`（logical + physical/scale）。
- 依赖 **target-gated**，仅 macOS/Windows 引入：`xcap`（截图）、`enigo`（输入合成，含 `Mouse::location`）、`image`（缩放 + PNG 编码）。用 `[target.'cfg(any(target_os = "macos", target_os = "windows"))'.dependencies]` 隔离，**Linux 构建不引入这些 crate**、公共 API 返回 `Unsupported`。`base64` 复用 workspace。

### B. 坐标缩放（正确性关键）
捕获 physical 像素 → 下采样到目标分辨率（config `target_max_dim`，默认约 1280；`computer_20251124` 支持长边至 2576px，可配）→ 上报 `display_width/height_px` = 目标尺寸 → 模型返回坐标按 `physical/target` 比例映射回 physical 像素再合成输入。处理 Retina/HiDPI scale factor（截图 physical、光标 API 多为 logical points，需按 scale 归一）——列为已知复杂点，先在 macOS 打磨。

### C. `crates/api`：原生工具注入 + beta header
- 扩展 `ToolDefinition`（`crates/api/src/types.rs:124-129`）：新增 `native: Option<NativeToolSpec>`；`NativeToolSpec { tool_type: String, extra: serde_json::Value, beta: &'static str }`。加 helper 构造器 / 派生 `Default`，其余工具置 `None`（机械改动）。
- `anthropic.rs` 构建 tools（`:387-397`）分支序列化：native → `{type, name, ...extra, [cache_control]}`（**无 description/input_schema**）；custom → 现状。`ApiRequest.tools` 由 `Vec<ApiTool>` 改为 `Vec<serde_json::Value>`。
- beta header（`anthropic.rs:441-450`）：任一工具带 `native.beta` 时追加（`computer-use-2025-11-24`）。
- OpenAI provider：跳过 native 工具（本不支持）。

### D. `crates/tools`：`ComputerTool`（`crates/tools/src/computer.rs`，`#[cfg(any(macos, windows))]`）
依赖 `wyj-computer`，实现 `Tool`：
- `name() = "computer"`；`definition()` 返回 `native = Some(computer_20251124 + 主屏目标分辨率)`（运行时构造）。
- `needs_permission(input)` 按 `input["action"]` 分支：`screenshot`/`cursor_position`/`wait` → false；`left_click`/`type`/`key`/`scroll`/`drag`/... → true。
- `action_summary(input)`：如 `left_click @ (x,y)`、`type "…"`、`key ctrl+c`。
- `parallel_safe() = false`（串行，共享桌面状态）。
- `run`：解析 action 分派到 `wyj-computer`；`screenshot` → `ToolResult::with_parts(占位, [Image])`（照抄 `read.rs:110-116`），其余 → ack 文本（可配 action 后 auto-screenshot 减少往返）。
- 兜底集成：变更动作前查 `cursor_location`，近屏角阈值内 → 立即返回 abort；`Arc<AtomicUsize>` 单轮动作计数（回合起点重置），超阈值返回 `is_error` 提示模型停下请示。

### E. 权限：会话内放行（`crates/tools/src/ctx.rs`）
- `ToolCtx` 新增 `session_allowed: RwLock<HashSet<String>>`（永不落盘）+ `session_scoped_tools: HashSet<String>`（含 `"computer"`）。
- `confirm_tool` 短路：命中 `always_allowed || session_allowed` 即放行。
- `AllowAlways`：`name ∈ session_scoped_tools` → 进 `session_allowed`（不 persist）；否则现状（`always_allowed` + `persist_allowed_tools`）。弹窗文案提示"（仅本会话）"，走 i18n。

### F. 注册与门控
- 各注册路径（headless 主路径 `crates/cli/src/main.rs:483+`、`/model` 重建 `:868-882`）：当 `cfg!(any(macos, windows))` && `active_profile().vision` && `active_profile().is_official_anthropic_endpoint()` 时 `register_arc(ComputerTool)`——**不是**单纯 `provider == Anthropic`，见实施记录里的修复说明。子 Agent 注册表默认不含（与 Agent/AskQuestion 一致，后续可选）。
- macOS：首次运行需 Screen Recording + Accessibility（TCC）；preflight 检测失败时打印 System Settings 授权指引。Windows：per-monitor DPI aware；UAC 提权窗口非提权进程无法控制（已知限制）。

### G.（可选）`/computer` 诊断命令
展示启用状态、主屏尺寸/目标分辨率、平台权限检测结果（纯只读）。**若新增，必须同步 `help.body`（`crates/i18n/locales/{en,zh}.yml`）与 i18n key**（CLAUDE.md 硬性约定）。

## 复用的既有能力（不重复造）

- 权限弹窗：`confirm_tool` / `UiAskRequest::ToolPermission` / `PermissionDialog` / `draw_permission_dialog`（无需新 UI）。

- 编码：workspace 已有 `base64`/`png`。

## 分阶段实施
1. **API 层**：`ToolDefinition.native` + `anthropic.rs` 分支序列化 + beta header；单测断言线格式 JSON 与 beta 头。
2. **`wyj-computer` crate**：macOS backend（xcap 截图 + enigo 输入 + 光标位置 + 主屏尺寸/scale）+ 坐标缩放 + PNG 编码；Windows backend；Linux stub。

## 保留边界（v1.3.0 不做）
- Linux（X11/Wayland）不在首版。
- 浏览器专用自动化路径（Playwright/CDP）不做。
- 沙箱/VM 隔离运行不做（控制本机真实桌面）。
- 终端内渲染截图（Sixel/Kitty）不做——终端仅见占位文本，模型见像素。
- 子 Agent 默认不启用 computer。
- OpenAI provider 的 computer-use（其丢图，功能 Anthropic-only）。

## 验证
- 单测：坐标缩放数学、区域裁剪钳制（`clamp_region`）、action 解析、`needs_permission` 分支、native 工具序列化线格式 + beta 头、`session_allowed` 权限逻辑。

- **zoom 手测**（真正验证识别准确率是否改善，自动化测不了实际读数对错）：打开一个含密集小字/数字表格的界面（如股票自选股列表、Excel 密集单元格），让模型先 `screenshot` 定位大致区域，再观察它是否主动 `zoom` 进去读数字而不是直接从全屏截图里报数字；对比同一批数据在"仅全屏截图"和"配合 zoom"两种情况下模型报告的准确率差异。custom 模式（MiniMax 等第三方模型）重点验证，原生模式（官方 Anthropic）作对照。
