# wyj-code v1.2 计划

## Context

v1.1.0（Hooks 生命周期自动化 + 开源产品化基线）已完成待发布。wyj-code 作为个人工程作品集项目，
核心链路（26 命令 / 15 工具 / TUI / MCP·skills·plugins 三市场 / 子 Agent 编排 / 记忆 / 压缩 / i18n /
逐调用权限确认 / Hooks / 自更新）已经相当完整。

本轮规划围绕用户提出的四个方向做了一次头脑风暴 + 实测校准，最终把 v1.2 定为
**「自定义命令对齐真 CC」+ 三个轻量收尾项**：

- **头部特性**：对齐真实 Claude Code 的自定义 slash 命令能力。调研发现项目已有的
  **Skill 系统**（`crates/commands/src/skill.rs`）在功能上已经约等于真 CC 的自定义命令
  （扁平 `.md` 文件、`$ARGUMENTS` 模板替换、直接注册为 `/name` 命令），只是**路径没有对齐
  真 CC 的 `.claude/commands/` 约定**（用的是项目自造的 `~/.wyj-code/skills/`/`.wyj/skills/`），
  **frontmatter 也只是被跳过、没有解析出 `description`/`argument-hint`/`allowed-tools` 等结构化
  字段**。因此头部特性范围从"造一个新子系统"收窄为"扩展现有 Skill 加载器"，工作量和风险都显著
  更小，详细设计见下方「特性 1」。
- **工程打磨（轻量）**：用户最初提出"打包体积大、启动慢"的假设，实测后发现并不成立——release
  二进制 12MB、稳态冷启动 ~8ms，已经开了 opt-level=3/lto=thin/codegen-units=1/strip=true 且
  reqwest 用 rustls 而非 openssl。因此这一项收窄为「实测量化 + 处理可收敛的重复依赖 + 把真实
  数据写进 README/CHANGELOG」，而不是无的放矢地优化一个已经不存在的问题。
- **稳定性技术债（小范围）**：代码扫描发现 `crates/cli`/`crates/i18n`/`crates/mcp` 三个 crate
  零测试覆盖，`crates/tui/src/app.rs` 单文件集中 39 处 `.unwrap()`。本版本只做小范围补强，不追求
  覆盖率指标或"清零"。
- **传播打磨（轻量）**：README 已经相当完整，本版本只加一个 Demo 章节（录屏/GIF + 60 秒上手），
  不引入新基础设施。

## 特性 1（头部）：自定义 slash 命令对齐真实 Claude Code

**目标**：现有 Skill 系统（`crates/commands/src/skill.rs`）功能上已约等于真 CC 自定义命令，本特性
把它扩展到真正对齐——识别真 CC 路径、解析结构化 frontmatter、`allowed-tools` 执行期强制、`/help`
动态展示。核心复用点：`agent_def.rs` 里已有一个现成的通用 frontmatter 行级解析器（`parse_frontmatter`），
以及 Plan 模式已在用的 `PermissionMode::Allowlist` 工具白名单闸门——两者都不用重新发明，直接复用。

### 1.1 路径合并：六层链，真 CC 路径同作用域内胜出

在现有四层（builtin → 全局 `~/.wyj-code/skills` → 插件 if_absent → 项目 `.wyj/skills`）基础上，
在全局层和项目层各插入一层真 CC 路径，且**同作用域内真 CC 路径覆盖 wyj-code 自造路径**（用户从真
CC 迁移过来的命令应该权威，与项目一贯"越贴近真 CC 语义越优先"的哲学一致）：

```
1. builtin
2. 全局 wyj-code:  ~/.wyj-code/skills/*.md
3. 全局真 CC:      ~/.claude/commands/*.md         ← 覆盖 #2 同名条目
4. 已启用插件贡献路径（if_absent，先到先得，不变）
5. 项目 wyj-code:  .wyj/skills/*.md
6. 项目真 CC:      .claude/commands/*.md            ← 覆盖 #1-#5 同名条目，最高优先级
```

作用域优先级（全局 < 插件 < 项目）不变，只是同作用域内新增"真 CC 胜出"这一层。仅扫顶层 `*.md`，
不递归子目录（子目录里的文件本版本静默不加载，命名空间见 1.5），需在文档中显式提醒。

### 1.2 Frontmatter 解析：复用 `agent_def.rs` 现成解析器，不新增依赖

新建 `crates/core/src/frontmatter.rs`，把 `agent_def.rs` 里的 `parse_frontmatter`（逐行 `key: value`，
处理 CRLF/未闭合/无 frontmatter 等边界，已有完整单测）提升为 `pub fn parse`，`agent_def.rs` 改为调用
它；`skill.rs` 通过 `wyj_core::frontmatter::parse` 复用（`commands` 已依赖 `wyj-core`，零新依赖）。

`SkillCommand` 新增 `argument_hint`/`allowed_tools`/`model: Option<String>` 三个可选字段，解析降级
规则（保证无 frontmatter 的现有内置/用户 skill 行为零变化）：

| 字段 | 有值 | 缺失 |
|---|---|---|
| `description` | 直接用，不再剥离正文里的 `# 标题` 行 | 回退现有逻辑：扫描首个 `# ` 行，找不到用文件名 |
| `argument-hint` | `usage_str` 改为 `/{name} {hint}` | 保持 `/{name} [$ARGUMENTS]` |
| `allowed-tools` | 逗号切分成 `Vec<String>`（照抄 `agent_def.rs` 的 `tools` 字段解析） | `None`，行为不变 |
| `model` | 存字符串，**本版本只存不生效**（见下） | `None` |

未识别字段静默忽略。现有 5 条 skill.rs 测试必须全部保持通过，这是"不破坏现状"的可执行验证。

### 1.3 `allowed-tools` 执行期强制：复用 Allowlist，临时收紧、跑完还原

新增 `CommandResult::RunPromptScoped { text, allowed_tools: Option<Vec<String>>, profile: Option<String> }`
（不改动现有 `RunPrompt`，避免动到 `/init` 等已有构造/消费点）。`SkillCommand::run` 仅当命令带
`allowed-tools`/`model` 时返回这个新变体，否则和今天完全一样返回 `RunPrompt`。

消费端（TUI `app.rs` 与 headless `cli/main.rs` 各一处，模式相同）：读出当前 `permission_mode` 快照 →
换成 `PermissionMode::Allowlist(该命令的 allowed_tools)` → 跑这一轮 `run_turn` → 无论成功失败都换回快照。
**不改 `AgentMode`（Normal/Plan/Bypass）本身**，状态栏显示不受影响，只是这一轮的底层闸门临时收紧。

已知子集限制（需写进文档）：`Allowlist` 只做整工具名级别匹配，不支持真 CC 的 `Bash(git status:*)`
这类命令级细粒度限制，`allowed-tools` 因此只能到"允许/不允许用某个工具"的粒度。

`model:` 字段本版本**只解析存储，不做运行期切换**——运行期临时换 Agent 涉及 Session 共享、token
统计归属等需要额外小心处理的细节，风险与工程量明显高于另外三个字段，先解析存储保证后续加运行期
支持时不用再改 frontmatter 格式（向前兼容），运行期真正生效推到 v1.2 收尾富余时间或 v1.3。

### 1.4 `/help` 动态展示

`Command` trait 新增带默认实现的 `fn is_dynamic(&self) -> bool { false }`（不影响任何现有实现的
编译），`SkillCommand` 覆盖为 `true`。`CommandContext` 新增 `dynamic_commands: Vec<(String, String,
String)>` 字段，沿用 `effective_mcp_count`/`plugin_agent_paths` 的既有模式——调用方在构造 `cmd_ctx`
前用 `cmd_registry.list()` 过滤 `is_dynamic()` 算好传入。`HelpCmd` 渲染完静态 `help.body` 模板后，若
`dynamic_commands` 非空，追加一个"自定义命令"分组（i18n 新增 `help.custom_commands_header` key）。

CLAUDE.md 的"新命令必须同步进 `/help` 模板"约定对静态内置命令依然成立不变；需要补一句说明动态命令
走 `ctx.dynamic_commands` 追加展示、不进静态模板，两者互不冲突，避免以后误解。

### 1.5 命名空间：明确推迟到 v1.3

真 CC 的 `.claude/commands/<subdir>/<name>.md` → `/subdir:name` 命名空间需要改动命令名解析、
`dispatch`/`complete`、插件冲突判定等多处"文件名 stem = 命令名"的假设，是独立可拆分的增量特性，
不影响本次四项核心交付，本版本不做，子目录文件静默不加载并在文档中提示。

### 改动文件清单

| 文件 | 改动点 |
|---|---|
| `crates/core/src/frontmatter.rs`（新建） | 从 `agent_def.rs` 搬迁 `parse_frontmatter` → `pub fn parse` |
| `crates/core/src/agent_def.rs` | 改为调用 `crate::frontmatter::parse` |
| `crates/core/src/lib.rs` | 新增 `pub mod frontmatter;` |
| `crates/commands/src/skill.rs` | 新增三字段解析、`.claude/commands` 路径合并、`is_dynamic()`、`RunPromptScoped` 分支 |
| `crates/commands/src/registry.rs` | `CommandResult::RunPromptScoped`、`Command::is_dynamic()`、`CommandContext.dynamic_commands` |
| `crates/commands/src/builtin.rs`（`HelpCmd`） | 消费 `dynamic_commands` 追加动态分组 |
| `crates/tui/src/app.rs` | `CommandContext` 构造补字段；新增 `RunPromptScoped` 分支（临时 Allowlist + 还原） |

### 交付顺序

1. `frontmatter.rs` 抽取 + `agent_def.rs` 迁移（先验证不破坏其现有单测）。
2. `skill.rs` frontmatter 三字段解析 + 单测（纯解析层，先不动路径/执行期限制）。
3. `.claude/commands` 六层路径合并 + 单测（覆盖同名冲突方向）。
4. `RunPromptScoped` + `allowed-tools` 的 TUI/headless 消费端（工程量最大，单独验证）。
5. `/help` 动态分组 + i18n + CLAUDE.md 文档同步。
6. （视时间富余）`model:` 字段运行期支持，否则明确推到 v1.3。

## 特性 2（轻量）：构建体积与启动速度——实测量化 + 依赖去重

**背景**：实测数据（本次调研，`cargo build --release` + `time`/手动计时）：

| 指标 | 数值 |
|---|---|
| release 二进制体积（已 strip） | 12 MB |
| debug 二进制体积（`cargo run` 默认） | 64 MB（未 strip/未优化，符合预期，非缺陷） |
| 稳态冷启动（`--config-status`，无 TUI 无网络） | ~8ms |
| 换新二进制后首次执行 | 87ms ~ 1.2s（OS 可执行文件页缓存预热，非程序问题） |

结论：release 产物已经比较精简（已开 `opt-level=3`/`lto="thin"`/`codegen-units=1`/`strip=true`，
`reqwest` 已用 `rustls-tls` 避免捆绑 OpenSSL），不存在"体积很大"的问题；启动速度稳态已接近瞬时。
因此本项收窄为轻量的量化 + 去重收尾，不作为需要大改的头部工程：

- **`cargo tree --duplicates` 已发现的多版本依赖**：`bitflags`(1.3/2.13)、`getrandom`(0.2/0.3/0.4)、
  `hashbrown`(0.15/0.17)、`itertools`(0.11/0.13)、`rustix`(0.38/1.1)、`schemars`(0.8/1.2)、
  `unicode-width`(0.1/0.2)。逐条判断能否收敛：
  - 若冲突是本项目直接依赖的版本落后于传递依赖使用的新版本（例如 `unicode-width`/`itertools`/
    `schemars` 若是 `Cargo.toml` 里直接声明的），尝试升级到与传递依赖一致的版本，跑
    `cargo tree --duplicates` 确认收敛。
  - 若冲突是上游库之间的 SemVer 主版本不兼容（`getrandom` 三版本共存、`bitflags`/`rustix` 两个
    major 并存大概率属于此类——分别被 `rmcp`/`arboard`/`crossterm` 等不同上游库各自锁定），
    这类无法靠本项目升级解决，如实记录「哪些能收敛、哪些不能」，不承诺不现实的结果。
- **首次安装 `cargo-bloat`（本地 dev 工具，不影响发布产物）**，跑
  `cargo bloat --release --crates` 和 `cargo bloat --release -n 50`，取 crate 级/函数级体积贡献
  Top 列表，作为是否有进一步可砍依赖的判断依据（比如 `scraper`/`zip+tar+flate2`/`rmcp` 等偏重的
  依赖，本项目"单二进制"设计原则决定了不能用 Cargo feature 拆分发布产物，所以能做的只是"换更轻的
  替代库"或"确认现状已是必要成本"，不强求砍掉功能）。
- **`panic = "abort"` 明确决定不采用**，并记录原因：项目大量使用 `tokio::spawn`（后台记忆提取、
  子 Agent、bash 后台会话），当前若某个 spawned task panic，只是该 task 失败（`JoinError`），不影响
  主进程；一旦切到 `panic="abort"`，任意线程 panic 会让整个进程（包括用户正在用的 TUI 会话）立刻
  退出，这个行为回归对一个交互式 TUI 应用是不可接受的取舍，在体积收益前不划算，本版本不做。
- **交付物**：把实测数据（体积、启动耗时、去重前后的 `cargo tree --duplicates` 输出对比）写进
  README「已知限制」附近或新增一个简短「性能」小节，以及 CHANGELOG 对应条目——用真实数字回应
  "体积大不大"，而不是模糊表述。

## 特性 3（轻量）：稳定性技术债小范围补强

**背景**：扫描发现（本次调研）：
- `cargo test --workspace` 目前全绿、0 ignored；但测试分布不均——`crates/cli`、`crates/i18n`、
  `crates/mcp` 三个 crate **完全没有单测**（core 42 / store 53 / tools 33 / tui 73 / api 11 /
  commands 8 / config 5 个 `#[test]`，这三个是 0）。
- `crates/tui/src/app.rs` 单文件 **39 处 `.unwrap()`**：多数是 `RwLock::read/write().unwrap()`
  （锁中毒才 panic，风险较低，属于既有惯用法）和 `xxx_dialog.as_ref().unwrap()`（内部不变量，
  正常路径下不为 `None`）。但也有个别真正外部输入可达的风险点，例如 `app.rs:3654`
  `read_output.lines().next().unwrap()`——若 bash 输出恰好是空字符串会直接 panic。

**本版本范围（不追求覆盖率指标或清零）**：
- 为 `crates/cli`/`crates/i18n`/`crates/mcp` 各补最基础的冒烟测试：
  - `i18n`：`tr()`/`tr_fmt()` 在中英文两个 locale 下对已存在 key 的取值正确、`set_locale` 切换生效。
  - `mcp`：`bridge.rs` 桥接逻辑的基本单元测试（构造/生命周期，若涉及真实进程可用 mock/最小 stdio
    echo server）。
  - `cli`：对几个关键 CLI flag（`--config-status`/`--no-hooks`/`--plan`/`--bypass-permissions`）
    的参数解析行为做测试，不要求覆盖整个 `main()` 流程。
- `app.rs` 里挑出"外部输入可直接触发"的高危 `unwrap()`（如上面 `:3654` 这类），改成有意义的降级
  处理或 `expect()` 附带说明；其余锁相关/内部不变量相关的 `unwrap()` 维持现状，不做无意义改动。

## 验证（端到端）

- **自定义命令 — 路径合并**：`~/.claude/commands/foo.md`、`.claude/commands/foo.md`、
  `~/.wyj-code/skills/foo.md`、`.wyj/skills/foo.md` 同名放置，验证六层顺序逐层生效、真 CC 路径
  在同作用域内胜出（单测仿照 `skill.rs` 现有 4 条集成测试写法）。
- **自定义命令 — frontmatter**：单测覆盖 `description`/`argument-hint`/`allowed-tools`/`model`
  四字段独立与组合场景；现有 5 条 `skill.rs` 测试必须保持通过（无 frontmatter 行为零变化的回归线）。
- **自定义命令 — allowed-tools**：tmux 手测，挂一个 `allowed-tools: Read, Grep` 的命令，触发后在该
  轮尝试用 Bash/Write 应被拒绝；命令结束后下一轮应恢复原权限模式，Normal/Plan/Bypass 三种模式各测
  一遍，确认状态栏显示的 `AgentMode` 未被误改。
- **自定义命令 — /help**：放一个自定义命令后 `/help` 末尾出现"自定义命令"分组，卸载/禁用后消失；
  确认 `is_dynamic()` 默认方法未导致既有内置命令编译报错。
- **体积/启动**：`cargo build --release` 后 `ls -lh target/release/wyj-code` 体积对比优化前记录值；
  `cargo tree --duplicates` 去重前后对比；README/CHANGELOG 数据人工审阅。
- **稳定性**：`cargo test --workspace` 新增测试全绿；`app.rs` 修改点手动复现原 panic 场景确认修复
  （如构造空字符串 bash 输出走一遍对应代码路径）。
- **README Demo**：人工审阅录屏/GIF 可正常播放，60 秒上手命令块实机跑通。
- **回归**：`cargo build --release`、`cargo test --workspace`、`cargo clippy --workspace --all-targets`、
  `cargo fmt --check` 全绿。
