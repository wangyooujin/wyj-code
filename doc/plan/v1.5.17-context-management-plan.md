# 上下文管理改造计划（v1.5.17）

> 状态：**第 1-3 批已全部实施**（决策记录见 §5）。
> 背景调研见本文档「业界实践基线」，区分了官方文档硬事实与社区推测。

## 0. 问题陈述

wyj-code 的上下文由**三条口径互不一致的链路**分别度量：

| 用途 | 口径 | 位置 |
|---|---|---|
| 决定要不要压缩 | `estimate_request_tokens`（system + tools + 输出预留 + framing） | `core/src/compact.rs` |
| 状态栏显示百分比 | `estimate_tokens(messages)`（**只有 messages**） | `core/src/render.rs::draw_status` |
| 记忆注入上限 | 8,000 **字节**硬截断 | `core/src/memory_v3.rs` |

差距实测：主 system prompt ≈ 2,245 tokens + ≥16 个常驻工具 schema + `max_tokens` 8,192 + 协议开销 —— **至少 1.3 万 token 不在进度条里**，在 200K 窗口下就是 ≥6.5 个百分点的系统性低报。进度条的颜色和实际压缩时机对不上号。

## 1. 业界实践基线（2025-2026 调研）

### 硬事实（有官方文档 / 源码支持）

- **Claude Code 官方文档明确承认 statusline 百分比与压缩时机脱节**：
  > "The status line's `used_percentage` always measures against the model's full context
  > window, so once [`CLAUDE_CODE_AUTO_COMPACT_WINDOW`] is set, that percentage no longer
  > indicates when compaction will run."
  （[env-vars](https://code.claude.com/docs/en/env-vars)）
- **Claude Code 官方明确输出上限会挤压压缩预算**：
  > "`CLAUDE_CODE_MAX_OUTPUT_TOKENS` — Increasing this value **reduces the effective
  > context window available before auto-compaction triggers**"（同上）
  → 直接支持「压缩 buffer 必须 ≥ `max_tokens`」这条设计。
- **Claude Code 内置 UI 不再默认展示 context 百分比**（社区多篇报道 + 官方
  interactive-mode 快捷键参考中无该控件）。官方措辞是 **"Context left until
  auto-compact"**（剩余量语义），不是"已用百分比"。
- **Claude Code 先清旧工具输出，再考虑摘要**（[how-claude-code-works](https://code.claude.com/docs/en/how-claude-code-works)）：
  > "It clears older tool outputs first, then summarizes the conversation if needed."
- **Anthropic context editing**（`context-management-2025-06-27` beta）：
  `clear_tool_uses_20250919` 默认 `trigger = 100,000` input tokens、`keep = 3`；
  按时间顺序清最旧的，替换为占位；**客户端保留完整未修改历史**；
  ⚠️ **清理会击穿 prompt cache 前缀**。
  官方 benchmark：memory tool + context editing **+29%~+39%**；
  100 轮 web search 评测 **84% token 减少**。
- **Codex CLI**：`min(config, window × 0.9)` + 独立的 `window × 0.95` 硬线；
  rollout append-only 落盘，压缩点写独立检查点行（含 `replacement_history`），
  **UI 历史列表按整条 rollout 重建，压缩事件只标记不删除**。
- **Goose**：`compute_tool_call_cutoff = clamp(3 × limit / 20000, 10, 500)` ——
  **保留量随窗口线性伸缩 + 双侧钳制**；非法阈值回退默认值而不报错；
  每批只处理 10 个；**当前轮的工具调用永不摘要**。
- **Cline**：`TRIGGER = 0.9` 但 `TARGET = 0.7` —— 压缩后落到 70% 而非贴着线跑。
- **Aider**：`min(max(max_input/16, 1024), 8192)`；摘要提示词强制
  "MUST include 函数/库/包名和代码块里的文件名" + "MUST NOT 包含代码块本体"
  + "不要用 'Finally...' 收尾"。
- **Cursor**：context ring 点开可看 8 类 token 分解（含 Summarized conversation）；
  长工具输出**写文件 + 给 agent 读取能力**（实测 token 降 **46.9%**，
  "fewer unnecessary summarizations"）；达上限后**给 agent 一个历史文件引用**，
  让它自己去搜回摘要里缺的细节。

### 已一手核实的失败模式

| 现象 | 出处 |
|---|---|
| 自动压缩无预警，摘要里提到的历史动作被下一轮**误读为待执行指令** | claude-code #68097（closed as not planned） |
| 压缩静默销毁 6 小时会话的活跃工作，模型花 30+ 分钟搜自己写过的内容 | claude-code #47145（closed as not planned） |
| 压缩把 "Respond with TEXT ONLY. Do NOT call any tools" 当活约束重放 → 会话变砖 | claude-code #49806 |
| 压缩把 `.claude/rules/` 指令叙述成"正在检查"而非"待重新验证的约束" | claude-code #27993 |
| `/compact` 摘要 API 失败时**先删原对话再调摘要**，失败被伪装成成功 | v2.1.112 |
| Thrashing（压缩后立刻回满，反复烧 API） | 官方 troubleshooting，Claude Code 会主动停止重试 |

**Drew Breunig 的四分类**（社区广泛复述）：Poisoning（幻觉被洗白成决定）/
Distraction（摘要太啰嗦，重造膨胀）/ Confusion（多余细节把 agent 拉偏）/
Clash（摘要与实时消息互相矛盾）。另有**代际复利**（compaction amnesia）：
turn 3 设的约束经三代改写后失真。

**什么最先死**（[debugly.dev](https://debugly.dev/agent-context-compaction-loss)）：
**负知识**（被否决的假设）、**精确值**（路径/行号/常量）、**顺序因果**。
这三类恰好是 LLM 摘要最擅长丢的。

**Context Rot**（[Chroma 2025](https://www.trychroma.com/research/context-rot)）：
18 个模型全部随输入变长而退化；反直觉发现是**打散局部连贯性反而提升表现** ——
对"把整个文件按原顺序塞进上下文"是一个反证。

### ❌ 明确未查到（不要当事实引用）

   流传的 95% / 80% 均无官方出处）
2. Claude Code 的**预留 buffer 具体 token 数**（三套矛盾数字 13K/20K/33K，全为逆向推测）
3. Cursor 的自动摘要阈值百分比（官方从未公布）
4. Aider 的 `/compact` 命令**根本不存在**（逐版本 grep 验证）
5. Cline 的常量是 0.9×0.9=0.81，**不是流传的 0.8**

## 3. 第 3 批：tool_result context editing（已实施）

### 3.1 为什么值得做

`/context` 现在已经能如实报出「可回收的旧工具结果」有多少 token（超过最近
`RECLAIM_KEEP_RECENT_TOOL_CALLS = 3` 个的全部 tool_result）。这些内容：

- **当前 100% 被浪费**——它们占着窗口直到被整段 compact 摘要，而摘要把它们
  压成一行 `[工具输出] xxx…`，负知识 / 精确路径 / 顺序因果全丢；
- 清理**比摘要便宜**（无 output token、不花钱、不会幻觉），且**更保真**
  （原文还在，只是移出模型视野）；
- Anthropic 官方 benchmark：context editing 单项 +29%，100 轮 web search
  场景 token 降 84%。

### 3.2 核心架构决策：模型可见历史 ≠ 持久 transcript

这是本批**唯一的真问题**，必须先定。当前 `Session.messages` 同时扮演两个角色：

1. 发给 provider 的请求内容（in-memory）
2. 落盘的 `session.json`（用户可以 `/resume`、可以 `/rewind` 的事实来源）

如果就地替换 tool_result，**transcript 就永久丢了内容**。业界三个成功项目在
这一点上做法一致，且都选了「追加式 + 压缩点标记，不就地删除」：

- Claude Code：原文永远在 `~/.claude/projects/*/*.jsonl`，压缩只改"发给模型的那份"
- Codex：`RolloutItem::Compacted` 写独立行含 `replacement_history`，UI 历史按整条 rollout 重建
- Cursor：context 满了给 agent 一个**历史文件引用**，让它自己去搜

**推荐方案：CAS 外置（复用现成基础设施）**

`crates/core/src/workspace_cas.rs` 已有 `intern()`（SHA-256 去重 + ref_count）
和 `get()`，`serialize.rs` 已有 `cas://` URI 前缀与 `materialize_block` 的
materialize 往返。扩到 text 型 tool_result 只需要：

```
清理时:  原文 → cas.intern(bytes) → hash
         block 换成占位文本，内嵌 cas://<hash> + 一行召回指引
召回时:  新工具 ContextRecall { hash } 或复用 Read 读 cas:// URI → 原文回填
         （回填时把该条标记为「已召回」，不重复计入可回收量）
```

**为什么不选另外两条**：

| 方案 | 问题 |
|---|---|
| B. 只占位、靠模型重跑工具 | Bash / WebFetch / MCP 是一次性的，重跑拿不回原文。Cursor 之所以要写文件正是这个原因 |
| C. 维护 `SessionArchive` 并行副本 | 要改 `SessionStore::save` / `load` / checkpoint / branch / rewind 全链路，且 archive 与 messages 的一致性是长期负担 |

### 3.3 待定的策略参数

| 参数 | Anthropic 默认 | 建议 | 说明 |
|---|---|---|---|
| `trigger` | 100,000 input tokens | 按窗口比例，如 `cw/4` | 固定 100K 在 1M 窗口下几乎不触发 |
| `keep` | 3 个 tool use | 3（沿用 `RECLAIM_KEEP_RECENT_TOOL_CALLS`） | 最近 3 个必须保全文 |
| `exclude_tools` | 无 | **必须排除** `Edit`/`Write`/`NotebookEdit` 的成功回执 | 写操作回执丢了模型会重做 |
| `clear_tool_inputs` | false | false | 保留 `tool_use.input`（模型才知道自己调过什么） |
| 单批处理量 | — | 10 | 对齐 Goose，防一次性大手术 |
| 当前轮保护 | — | 当前 turn 的 tool_result 永不清理 | 对齐 Goose |
| 最小清理量 | `clear_at_least` | 有 | 避免为几十 token 击穿 cache |

### 3.4 已知风险

1. **prompt cache 击穿**：清理必然改写前缀（Anthropic 官方明写）。缓解：
   一次清理一批（≥ `clear_at_least`），并让 `/cost` 区分「正常 miss」与
   「上下文编辑导致的预期 miss」——**这一项建议留到更后面**。
2. **误删仍在用的结果**：模型可能刚 grep 完 20 轮前的内容要引用。缓解：
   占位符里带**工具名 + 一行内容摘要 + 大小**，让模型判断要不要召回，而不是
   只留一句 "removed"。
3. **Context Rot 的反直觉结论**：打散局部连贯性反而提升表现 —— 清理 tool_result
   恰好是「打散」，理论上是加分项，但需要实测确认没有反效果。
4. **CAS 生命周期**：`WorkspaceCas::gc` 目前**只被单测调用**，生产路径无消费点
   （CLAUDE.md「已知缺口」）。本批会让 CAS blob 量级上一个台阶，**必须同时
   确认 gc 有生产消费路径**，否则会变成新的存储泄漏。

### 3.5 建议的分期

| 期 | 内容 | 风险 |
|---|---|---|
| 3a | 纯只读：加 `ContextRecall` 工具 + `/context` 面板里可展开看被清理了什么（先不真清理） | 极低 |
| 3b | 真清理，但**只对 `Bash` / `WebFetch` / `Grep` / `Glob` 的结果**做 CAS 外置，Read/Edit/Write 一律不动 | 中 |
| 3c | 扩展到 Read；接 gc；`/cost` 区分预期 miss | 中 |

### 3.6 建议的验证方式

Anthropic 官方给的是 agentic search +29%。本项目可复用的自证方式：

- 在 `crates/core/src/compact.rs` 加 benchmark 式单测：构造 N 轮含大 tool_result
  的会话，对比「清理前 / 清理后 / 摘要后」三者的 `estimate_request_tokens`；
- 端到端用 `doc/` 下的真实 session 重放，观察模型在清理后是否仍能正确引用
  清理前读过的文件路径与行号。

## 4. 未纳入本计划的已知缺口

- **压缩会摧毁记忆检索质量**（第 4 批）：`agent.rs::memory_query_context` 与
  `build_memory_snapshot` 取最近 4 条 **User 角色**消息当检索 query，而 compact
  把 `session.messages` 重写成 `vec![summary]` 且该摘要 **role = User**；同时
  `MEMORY_SNAPSHOT_REFRESH_TURNS = 10` 的分桶计数也按 messages 里的 User 数算，
  被压缩重置。长会话压缩一次后，整段会话的记忆注入都建在摘要文本上。
- **压缩不可回看**：原文只存在于当轮开始前的 `AutoUser` checkpoint（上限 20/session）。
  业界通行做法是 append-only transcript + 压缩点标记（见 3.2）。
- **压缩提示词可补 Aider 的三条硬约束**（MUST 保留函数/库/包/文件名；
  MUST NOT 保留代码块本体；MUST NOT 以 "Finally/综上所述" 收尾）——现有 7 段模板
  只覆盖了第一条。
- **`COMPACT_ACK = "Understood. Continuing from the summarized context."`**
  鼓励模型显式提及摘要。Goose 的对治方案是 "Do not mention that you read a summary"，
  但那是双刃剑（用户就看不到压缩发生过）。wyj-code 走的是「显式系统消息 +
  状态栏计数」路线，**不要**改成静默。

## 5. 第 3 批的决策记录（2026-10-08）

四个岔路口的选择与理由，实施后回填：

| 决策点 | 选择 | 理由 |
|---|---|---|
| 实施范围 | **全量 3a+3b+3c 一次做完** | 只读观测期拿不到真实数据，分期反而让"清理到底省不省 token"只能靠推演 |
| 原文保存 | **CAS 外部化** | 复用现成的 SHA-256 去重 + ref_count + `cas://` 往返；另外两案要么不可逆、要么放弃去重 |
| 回收策略 | **会话结束时 release + 启动时 gc** | 语义与现有 CAS 一致，无需新机制；`gc` 此前只被单测调用，这次有了真实生产调用点 |
| 清理时机 | **与压缩阈值联动（清理优先于摘要）** | 对齐 Claude Code 原话；清得动就省掉一次 LLM 往返 + 一份摘要的 output token |

### 实际落地

- 新增 `crates/core/src/context_edit.rs`：`elide_tool_results` / `materialize_elided` /
  `recall_elided` / `release_session_blobs` / `elided_count`。
- 新增 `crates/tools/src/context_recall.rs`：`ContextRecall` 工具（按 hash 取回、
  支持 `offset`/`max_bytes` 分页、按 char boundary 切分防 CJK 损坏、hash 必须是
  32-64 位 hex 以挡路径穿越）。**进 `ALWAYS_VISIBLE_TOOL_SCHEMAS`** —— 一旦被
  lazy 折叠，占位符里的 `cas://` 就成了死路。
- `Agent::elide_stale_tool_results`：超阈值时先清理、重估、达标就停手，仍超标才
  跑 `compact_session_until_fit`。单请求最多 `context_edit.max_batches` 批。
- 落盘/还原：`SessionFile.elided_blobs` + `SessionStore::load` 调
  `materialize_elided` 还原成完整上下文（resume 语义 = 新会话从头开始）。
- 回收：TUI `/clear`、TUI 退出、headless `/clear`、headless 退出四处 release；
  CLI 启动时按 `storage.cas_total_bytes` 跑一次 `gc`（这两个配置项此前因"无消费点"
  被删，本次恢复）。
- 主提示词新增 `# Context management` 段，教模型看到占位符就 `ContextRecall`、
  不要凭空猜内容。

### 偏离原设计的地方

**保护窗口从"最近 3 个工具结果"改为"按工具白名单 + 最近 3 个"。**
`ELIDABLE_TOOLS = [Read, Grep, Glob, Bash, WebFetch]`，用**白名单**而非黑名单：
新增工具默认不被清理。`Edit`/`Write`/`NotebookEdit` 的回执被清理会让模型以为自己
没改过从而重做，代价远高于漏删的收益。

**`ToolResult` 不携带工具名**（只有 `tool_use_id`），所以保护规则必须先扫一遍
`ToolUse` 块建 `id → name` 映射；找不到映射的历史会话块**保守跳过**。

**`Parts` 型工具结果（含图片）不参与清理** —— 图片已由
`serialize::externalize_block` 走 CAS，且还原路径要保持 image 语义。

**清理上限是 30 条/请求**（3 批 × 10）。100 轮 × 2.5K token 的会话需要 2 次
推理轮次才收敛到阈值内 —— 符合真实情况（每个工具轮次都会重跑一次），但也意味着
极端情况下清理会跨多个轮次逐步生效，而不是一次到位。
